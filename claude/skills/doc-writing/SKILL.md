# 문서 작성

문서·발표자료의 **산문**을 쓰거나 고칠 때 적용한다. 모든 문서 작업의 기준이다.
프로젝트별 템플릿·해상도·CSS 같은 구체값은 문서가 속한 프로젝트의 `CLAUDE.md` 에 두고 여기에는 옮겨지는 원칙만 적는다.
프로젝트 밖에서 쓰는 문서는 전역 규칙만 따른다.

## 쓰기 전에 캐묻는다

문서를 쓰거나 고치기 전에 사용자에게 캐묻는다. 독자와 담을 내용은 사용자가 아는 사실이라 짐작으로 채우지 않는다.

- 문서가 속한 프로젝트의 `CLAUDE.md` 가 결정·용어의 정본 문서를 지정했으면 `grill-with-docs`, 지정이 없거나 프로젝트 밖에서 쓰는 문서면 `grill-me` 로 캐묻는다.
- 첫 질문은 독자다. 누가 읽는가, 그 독자는 무엇을 알고 무엇을 모르는가, 읽고 나서 무엇을 할 수 있어야 하는가를 하나씩 추천 답과 함께 묻는다. 사용자가 이미 말한 것은 다시 묻지 않고 추천 답으로 올려 확인만 받는다.
- 같은 주제의 문서가 이미 있으면 새 문서가 그 문서를 대체할 후보인지 옆에 두는 보조 문서인지 묻는다. 「옆에 다시 써 줘」 같은 요청도 여기에 해당한다.
- 계획·설계 문서는 정한 독자를 첫 화면에 「독자」 한 줄로 남긴다. 기존 계획·설계 문서를 고칠 때는 그 줄을 추천 답으로 쓰고 독자가 그대로인지와 이번에 바꿀 내용만 묻는다.
- 계획·설계 문서는 아래 질문에 답할 수 있을 때 캐묻기를 끝낸다. 섹션 이름은 정하지 않는다. 코드나 문서로 답이 나오는 것은 묻지 않고 직접 확인한다.
  - 무엇을 정했나
  - 왜 필요한가
  - 지금 확인된 상태와 이번에 바꾸는 것은 무엇인가
  - 하는 것과 안 하는 것은 무엇인가
  - 언제 끝났다고 보나
  - 아직 못 정한 것은 무엇이고 누가 정하나
  - 어떤 조건이면 되돌리나
  - 단계가 여럿이면 왜 그 순서인가. 무엇이 일정을 늦출 수 있나. 어디서 멈춰 다시 판단하나
- 캐묻기는 같은 세션에서 처음 쓰거나 고치는 문서마다 한 번 한다. 한 요청에서 문서를 여럿 다루면 그 요청의 캐묻기에서 문서마다 독자와 범위를 확인한다.
  캐물은 뒤 쓴 문서는 같은 세션에서 리뷰를 반영하며 다시 고칠 때 다시 묻지 않는다. 새 문서를 쓰거나 그 문서의 독자·목적이 바뀌면 캐묻기 스킬을 다시 부른다.
- 캐묻는 질문은 질문 창으로 낸다. 사용자가 일반 메시지로 답하면 훅이 그 답을 새 요청으로 본다.
  이미 받은 답은 다시 묻지 않는다. 캐묻기 스킬만 다시 불러 이번 요청의 캐묻기 상태를 되살린다.
- 사용자가 한 줄에 「캐묻기 생략」이라고만 쓰면 그 요청에서는 건너뛴다. 그 요청에서 쓴 문서는 캐물은 문서로 본다.
- 문서 파일을 쓰거나 고치기 전에 `doc-writing` 을 불렀는지, 이번 요청에서 캐물었거나 앞서 캐물은 뒤 쓴 문서인지는 `doc-skill-guard.py` 가 확인한다. 무엇을 문서로 보는지는 `~/.claude/hooks/testrun.py` 의 `is_document` 에 있다.

## 사람이 쓴 글로

AI 티를 뺀다(패턴 전수는 `humanize-korean` 스킬).

- **전각 대시(—)로 두 문장을 잇지 않는다.** 접속사나 마침표로 푼다.
- **상자·문단마다 첫 문장을 굵히지 않는다.** 굵기는 그 안에서 진짜 중요한 한 곳에만.
- **「A가 아니라 B」·「~기 때문입니다」 같은 틀을 연달아 쓰지 않는다.** 단정+부연의 균일한 리듬을 깬다.
- 비유·의인화·극적 수사 금지, 도메인 명사에 상태 동사 붙여 줄이지 않기(아래 「기술 사실을 비유로 쓰지 않는다」).
- **빼기만 하고 넣지 않는다** — 원문에 없던 상투구를 새로 만들지 않는다.
- **연결어미(~하고·~지만·~는데·~면서) 뒤에 쉼표를 찍지 않는다.** 나열 쉼표(A도, B도)는 예외다.
- **ASD-STE100 의 작성 규칙을 따른다.** 한 문장에 사실 하나 또는 지시 하나. 서술문은 어절 20개 안. 능동태로 쓰고 주어를 세운다. 같은 대상은 문서 전체에서 같은 낱말로 부른다. 한 낱말은 한 뜻으로만 쓴다. 절차는 명령형, 설명은 평서문이다. 한 문단은 한 주제이고 문장 여섯 안이다. 명사를 셋 넘게 잇지 않는다. STE 의 낱말 사전은 영어용이라 쓰지 않는다.
- **꾸민 문장을 쓰지 않는다.** 완곡한 말, 인상 표현, 수사, 군말을 뺀다. 사실·판단·지시만 남긴다. 예: 「시험 삼아 한 편에 돌린 결과」는 「독자 테스트를 문서 한 편에 한 번 실행했다」로 쓴다.

## 기술 사실을 비유로 쓰지 않는다

압축된 비유는 쓴 사람에게만 선명하다. 기준은 하나다 — 읽는 사람이 한 번에 이해하는가.
`humanize-korean` 이 안 잡는 축이라 문서 규칙으로 둔다.

| 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| 대가 | 영향 · 트레이드오프 |
| 막다른 분기 | 한 번 실패하면 다시 진행되지 않는 곳 |
| `X` 가 갖는다 · `X` 가 준다 | `X` 에 있다 · `X` 에 적혀 있다 |
| 인덱스가 이 조회를 받는다 | `(a, b, c)` 인덱스를 쓴다 |
| 서로 안 막는다 | 하나가 실패해도 나머지는 그대로 진행된다 |
| 유일한 문 · 유일한 자리 · 필요한 전부 | 여기서만 · 하나뿐 · 필요한 값이 다 들어 있다 |
| 죽는다 | 실패한다 |
| 조용히 낡는다 | 갱신되지 않은 채로 남는다 |
| jOOQ 로 간다 | jOOQ 를 쓴다 |

그 분야에서 통용되는 비유(큐·잠금·트리·상속)는 대상이 아니다. **그 분야 밖에서 끌어온 비유**만 걷는다.

**도메인 명사에 상태 동사를 붙여 줄이지 않는다.** 멈추는 것은 그 명사가 아니라
**그 명사에 일어나야 할 일**이다 — 「그 요청이 멈춘다」가 아니라 「그 요청은 처리되지 않는다」.

**은유를 은유로 바꾸지 않는다.** 「막다른 분기」를 「한 번 걸리면」으로 바꾸는 것은 나아진 것이 아니다 —
무엇이 잘못되는지 여전히 안 적혀 있다. 원인은 **실패**다.

## 밀도를 형식에 맞춘다

AI 티를 빼려다 **서술형으로 길어지지 않게.**

- 대시를 없앤 자리는 **짧은 마침표 문장**으로 끊는다. 서술형 연결어(~노릇을 한다·~인 것이지·~해 보고서야 알게 된)로 늘리지 않는다.
- 슬라이드·표·카드처럼 공간이 정해진 곳은 한 상자에 한 요점만 두고 형식명사(것·경우·부분)를 줄인다.
  **칸에 맞추려고 주어나 대상을 빼지 않는다.** 독자가 모를 말로 줄이지도 않는다. 안 들어가면 칸을 넓히거나 장을 나눈다.
  **명사 종결은 라벨 칸(제목·분류·상태·수치)에만.** 설명·결정·내용 칸은 주어와 동사가 있는 문장으로 쓴다. 「~할지.」 같은 조각으로 끝내지 않는다. 문장이 둘 이상이면 항목으로 나눈다.
- 경어체·평어체는 요소별로 일관되게 — 본문이 경어체여도 표 셀은 평어체 그대로.
- **한 항목에는 한 요점만 둔다.** 같은 요점을 설명하는 문장은 한 문단에 두고, 같은 위상의 요점이 이어지면 목록이나 표로 묶는다. 슬라이드처럼 줄 단위 배치가 필요한 형식에서만 문장 사이를 시각적으로 나눈다.
- **내용을 먼저 확인하고 형식을 정한다.** 표·카드의 칸을 채우려고 근거에 없는 주장·비교·단계·수치를 만들지 않는다. 내용이 형식에 맞지 않으면 칸이나 형식을 바꾼다. 비교 표는 행마다 같은 질문(무엇이 바뀌었나 등)에 답하도록 비교 기준을 먼저 정한다.

## 길어지면 그림을 검토한다

섹션 하나가 길어지면 글을 다듬기 전에 **형식을 먼저 의심한다.** 검토를 시작하는 신호는 셋이다.

- 한 섹션의 문단이 넷을 넘는다
- 같은 대상을 여러 문장이 다시 설명한다(「A 다음에 B 가 가고, B 는 C 안에 있고」)
- 읽는 사람이 위치·순서·관계를 머릿속에 다시 그려야 한다

### 무엇으로 바꿀지 순서대로 본다

1. **표·목록·코드 블록으로 접히는가.** 나열은 목록, 조건과 대응은 표, 형식은 코드 블록이다. 여기서 끝나면 그림은 필요 없다.
2. **남는 것이 좌표를 가진 정보인가.** 배치, 경로, 순서, 계층, 상태 전이, 시간 축이 그렇다. 그림이 맞는 자리다.
3. **그림에 담을 것을 한 문장으로 적어 본다.** 그 문장이 안 써지면 그림도 못 만든다. 내용이 아직 정리되지 않은 것이다.
   그 문장은 그림이 놓일 장이나 섹션 제목의 주장과 같아야 한다. 다르면 그림을 바꾸거나 그림의 자리를 옮긴다.

이유·판단·근거는 그림으로 바뀌지 않는다. 산문으로 둔다.
**글을 그대로 옮긴 그림과 빈 자리를 채우는 그림은 만들지 않는다.**

### 그림을 넣을 때

- 그림을 가리키는 문장 **바로 다음**에 둔다. 캡션에 무엇을 보는 그림인지 적는다.
- 그림은 본문 설명 없이도 캡션과 라벨을 함께 보면 위치·순서·관계가 읽혀야 한다.
- 구현의 근거가 되는 사실(상태 이름, 상태 전이, 순서 제약)은 그림에만 두지 않고 캡션이나 표에도 적는다. 본문에서 그림을 한 줄씩 다시 설명하지 않는다.
- 문서의 색 토큰을 그대로 쓴다. 다크 모드와 좁은 화면에서 글자가 잘리지 않는지 렌더로 확인한다(「실제 산출 형태로 확인한다」).
- 그림 안의 글자는 본문보다 작아진다. 라벨은 단어로 줄이고 설명은 캡션이나 본문에 둔다.

### 만드는 법

- 상자와 화살표 정도면 **HTML·CSS 나 인라인 SVG 로 직접 만든다.** 문서와 같은 색 변수를 쓰고 파일이 하나로 유지된다.
- 좌표 계산이 많은 구조도·배치도는 **Codex 에 맡긴다.** Codex CLI 에는 이미지를 만드는 명령이 없고 SVG·HTML 코드를 써 준다.
  문서에 그대로 넣고 색과 글자 크기를 고칠 수 있어 이 편이 낫다. 받은 코드는 렌더해서 확인한 뒤 넣는다.

## 무엇을 다루고 무엇을 가리키는지 분명히

- **제목은 주제를 앞세운다.** 설명 한 줄만 있으면 무엇을 다루는지 안 보인다. 주제·이름을 앞에 두고, 필요하면 줄바꿈해 설명을 붙인다. 작은 분류 라벨(eyebrow 등)에 기대지 않는다.
- **지시어 대신 대상명을 쓴다.** 「이 경로」「이 값」은 읽는 사람이 앞을 다시 봐야 한다. 경로·필드·상수 이름을 그대로 적는다.
- **문서 안에서만 통하는 내부 용어를 설명 없이 산문에 넣지 않는다.** 정의한 적 없는 말은 그 자리에서 기전으로 푼다. 분류 라벨로만 쓰는 것은 예외 — 그건 산문이 아니다.

## 독자에 맞춘 어휘

- **독자가 개발자인 기술 문서는 코드의 용어를 그대로 쓴다.** 정확한 용어(역직렬화·Enum·`DeviceEntity`·결과코드)를 쉬운 비유·풀어쓴 설명으로 눅이지 않는다 — "Enum 으로 변환" 을 "숫자와 뜻으로 남긴다" 로 바꾸지 않는다. 「표현」의 풀어쓰기는 낯선 용어를 대화에서 풀 때의 규칙이고, 이건 방향이 반대다.
- 동사 표준화: 행 생성 = **생성**, 값 확정 = **설정**, 값 읽기 = **조회**. 만든다/낸다/고른다/정한다 로 흩지 않는다.
- **한 문서에서 한 동사는 한 뜻으로만 쓴다.** 값을 `***` 로 바꾸는 일을 「가린다」로 쓴 문서에서 「대소문자를 가리지 않는다」처럼 구분한다는 뜻으로 다시 쓰지 않는다.
- **독자가 이미 아는 접두사·수식은 산문에서 생략한다.** 그 저장소 컨벤션이 정한 접두사(예: 공통 서비스의 `Common`)는 개발자가 아는 것이라 산문에선 줄인다. 클래스명·코드 블록·식별자는 원형 유지.

## 문서 종류에 맞춘 목소리

- **경험을 기록하는 글은 경험과 결정을 글쓴이의 범위 안에서 쓴다.** 개인 회고를 일반적인 정답처럼 단정하지 않는다. 같은 종결을 기계적으로 반복하지 않고, 지금도 하는 일은 현재형, 겪은 일은 과거형으로 쓴다.
- 회고·경험 글은 참고 자료 목록을 형식적으로 만들지 않는다. 주장을 직접 뒷받침하는 출처는 해당 문장에 링크하고, 여러 섹션에서 함께 쓰는 자료가 있을 때만 문서 끝에 모은다.

## 먼저 세우고 결론을 낸다

문서는 그 주제를 처음 보는 사람에게 **설명하는** 글이다. 결론만 박아놓으면 이해가 안 된다.

- **답을 이미 아는 사람만 아는 압축 라벨·은어를 쓰지 않는다.** 「get 인데 쓴다」·「왜 세트+1」처럼
  해독해야 뜻이 통하는 것은 안 된다. 항목 제목은 그것이 **무엇인지** 말하고, 설명은 기전을 사람 말로 푼다.
- **결정 섹션은 제목과 첫 문장에서 결론을 먼저 밝힌다.** 결론을 이해하는 데 필요한 용어만 먼저 정의한다.
  결론 뒤에 이유, 처리 방식, 경계 조건을 설명한다.
- **선택지를 내놓을 때는 판단 기준을 함께 적는다.** 근거가 있으면 추천하는 쪽에 추천 표시와 이유를 단다.
  근거가 모자라면 무엇을 확인해야 하는지와 누가 정하는지를 적는다. 아직 못 정한 항목도 선택지 없이 질문만 적지 않는다.
- **바꾸기·마스킹·변환을 설명할 때는 전과 후를 짝으로 싣는다.** 원문만 실으면 결과가 어떤 모양인지 독자가 짐작해야 한다.
- **독자가 다른 문서의 짧은 문체를 그대로 옮기지 않는다.** 형식은 따르되 내용은 세워서 설명한다.
- **쉽게 쓰려다 틀리지 않는다.** 귀에 붙는 요약·라벨이 사실과 어긋나거나 다른 장과 모순되면 안 된다.
  정본은 프로젝트 규칙이 정한다. 코드가 정본인 저장소도 있고 설계 문서가 정본인 저장소도 있다.
  지정이 없으면 코드가 정본이다. 코드로 알 수 없는 것은 사용자에게 확인한다.
  압축한 문장도 풀어 쓴 문장도 그 정본과 맞아야 한다. 정본과 대조하고 같은 문서의 다른 장과도 대조한다.
- 제목과 요약만으로 문서의 성격이 드러나지 않으면 첫 문단에서 무엇을 기록한 글인지 밝힌다. 요약을 첫머리에 두면 「요약」이라는 이름을 붙이고, 줄마다 역할(원칙·문제·대응 등)을 라벨로 구분한다.
- 수치와 상태 판단이 관측·계산·추정 가운데 무엇인지 독자가 혼동할 수 있으면 성격을 표시한다. 관측 근거, 계산식, 추정 근거를 함께 적는다.
- **한도·수치는 무엇을 세는지 처음 나오는 자리에 적는다.** 「로그 5,000개로 제한한다」만 쓰면 무엇을 1개로 세는지 알 수 없다.
  무엇을 1개로 세는지 정본이나 실행 결과로 확인한 뒤 단위와 함께 적는다.

## 문단·배치·제목

읽는 사람은 훑는다. 제목과 섹션의 첫 문장만 읽고 관심 있는 섹션만 내려간다. 글자 수 규칙은 두지 않는다.
길이는 참고값일 뿐이고, 읽히는가를 정하는 것은 문단을 어떻게 나누고 무엇을 어디에 두느냐다.
기준 실물은 토스페이먼츠 개발자센터의 「멱등성이 뭔가요?」(docs.tosspayments.com/blog/what-is-idempotency)다.
어휘·문장 구성이 사람이 쓴 글의 기준이다. 해요체만 평어체로 옮긴다.

- **결정을 말하는 섹션만 결론 문장 제목, 나머지는 명사구.** `##` 가 결정을 말하면 번호 + 결론(「차감은 원자적 조건부 UPDATE 한 문장이다」),
  설명·목록·색인 섹션이면 명사구(「문서 종류」). `###` 는 항상 짧은 명사구. 「문서는 세 종류다」처럼 설명 섹션을 억지로 문장으로 만들지 않는다. 회고·블로그 글은 글의 흐름과 분위기에 맞춰 제목을 정하며 이 형식을 강제하지 않는다.
  「개요」「배경」「결론」 같은 기능 이름 제목과 **제목 속 개수**(「근거 문서 두 편」)는 쓰지 않는다.
- **표 머리는 짧은 명사 한 단어**(「결정」「시나리오」). 「무엇을 왜 택했나」 같은 질문형·문장형 열 이름을 쓰지 않는다.
- **표 머리와 카드 칸 이름은 무엇을 담는지 뜻이 정해진 말로 짓는다.** 한 칸에는 그 이름에 맞는 내용만 넣는다. 「걸리는 것」처럼 뜻이 정해지지 않은 이름을 쓰면 질문·제안·영향이 한 칸에 섞인다.
- **대안을 비교한 표의 결정 칸은 그 저장소가 쓰는 결정 용어로 단다.** 「쓴다·안 쓴다」 같은 일상 동사 대신 그 저장소의 결정 문서가 이미 쓰는 말(채택·폐기 등)을 쓴다.
- **정보의 관계에 따라 형식을 고른다.** 비교·대응·조건별 차이는 표, 같은 위상의 원칙·조건·사례는 목록, 순서는 번호 목록이나 단계 흐름으로 표현한다.
- **표 셀에 문장이 둘 이상이면 문장마다 줄을 바꾼다.** 서로 다른 결정이면 행을 나눈다.
- **제목 바로 아래 첫 문장이 그 섹션의 주장이다.** 제목만 읽고 넘어가는 독자가 첫 문장에서 답을 얻는다. 제목을 되풀이하거나 뒤를 예고하는 문장은 쓰지 않는다.
- **독자가 따로 찾아볼 내용에는 소제목을 붙인다.** 결정 이유, 처리 흐름, 경계 조건, 확장 경로처럼 내용의 역할이 바뀌는 지점이 기준이다. 한 문단으로 끝나는 짧은 보충 설명에는 소제목을 만들지 않는다.
- **한 문단 한 요점.** 정의 문단, 예 문단, 대조 문단, 자기 결정 문단을 따로 둔다.
  일반 원리와 이 저장소의 결정은 문단을 가른다(「IETF 는 헤더를 표준으로 제안한다」 다음 문단에 「이 저장소도 헤더 방식이다」).
- **정의는 「정의 → 즉, 한 줄 요약 → 도메인 안의 예」.** 일상 비유(곱하기 1·절대값)는 쓰지 않는다.
- **표·코드·그림은 그것을 가리키는 문장 바로 다음에.** 「아래」로 가리킨다. 그림을 먼저 놓고 뒤에서 설명하지 않는다.
  표 밑에 출처 한 줄, 참고 자료 목록은 문서 끝에.
- **섹션 순서는 넓은 것에서 좁은 것으로.** 정의 → 왜 문제인가 → 기전 → 우리 결정 → 경계·거부 → 참고.
- **단계는 번호 목록, 한 단계 한 문장.** 분기는 3-1 / 3-2 로 가지를 달고, 보충은 그 단계 아래 들여쓴다.
- **원인과 결론이 이어지는 추론은 산문으로 쓴다.** 순서, 대응 관계, 같은 위상의 조건·원칙·사례는 목록이나 표로 구조를 드러낸다. 조각을 대시로 잇지 않고 「~기 때문에」「~라면」「반면」「또」로 한 문장 안에서 잇는다.
  이유 연결 「~기 때문에」는 열 문장에 한 번꼴을 넘기지 않는다.
- **가르치는 장치를 쓰지 않는다.** 독자가 상급자·채용 담당자·CTO 인 문서에서 질문형 제목, 「~살펴볼까요?」 같은 전환 질문,
  「알고 보면 쉽다」 같은 안심 문장은 뺀다. 「질문 → 답」은 「문제 문장 → 답」으로 바꾼다.
- **외래 기술 용어는 한글 표기 그대로**(리소스·타임아웃·헤더). 첫 등장에만 원어를 괄호로 한 번.
  은어는 「(일명 '따닥')」처럼 따옴표와 일명으로 한 번만.
- **행위자가 달라지거나 헷갈릴 수 있는 문장에는 주체를 쓴다.** 같은 문단에서 주체가 유지되고 오해할 여지가 없으면 반복을 생략한다. 피동은 상태를 말할 때만(저장되어 있던 응답) 쓰고, 행위자가 있으면 능동으로 쓴다.
- **동사는 도메인 명사 + 하다.** 구매·판매·선점·해제·차감·복원·승인·취소·재발급·측정·조회.
  사다·팔다·잡다·놓다·붙잡다·갚다·재다·묻다(시스템 사이) 같은 구어 동사를 쓰지 않는다.
  「부하로 잰」은 「부하로 측정한」으로, 「토스에 물어」는 「토스 조회 API 로 확인해」로 바꾼다. 「지금 살 수 있는지」는 「구매 가능 여부」다.
- **기술 동작을 구어로 줄이지 않는다.** 걸리다·돌다·깔리다·짜다와 「꼴」이 그렇게 쓰이면 구체적인 동작으로 바꾼다.
  「쿼리가 돈다」는 「쿼리가 실행된다」, 「이런 꼴로 보인다」는 「이런 형식으로 보인다」로 쓴다.
  시간·비용을 말하는 일상 용례(「작업에 5분이 걸린다」)는 그대로 쓴다.
- **「경합」은 락 경합처럼 자원을 두고 기다리는 상황에만.** 동시에 들어온 요청은 「동시 요청」「중복 요청」이다.
  처음 나오는 자리에서는 아래 규칙대로 한 번 푼다(「여러 요청이 같은 행을 동시에 수정하려다 서로 기다리는 것」).
- **독자가 모를 수 있는 분야 용어는 처음 나오는 자리에서 한 번 푼다.** 쿼리·정규식·조인·라벨·스트림처럼 옆 분야 사람이 모르는 말이 대상이다.
  기준 독자는 「쓰기 전에 캐묻는다」에서 정한 독자다. 슬라이드는 장마다 따로 읽히므로 그 장에서 처음 나오는 자리가 기준이다.
- **페이지·섹션·요소는 사람이 부르는 말로.** 「색인」이 아니라 「문서 목록」, 「결론 상자」가 아니라 「요약」.
  CSS 클래스명·내부 용어·「핫패스」 같은 정의한 적 없는 말을 산문에 쓰지 않는다.
- **옛 문장을 새 자리에 옮길 때도 이 규칙을 적용한다.** "나중에 고친다"며 그대로 싣지 않는다. 옮기는 순간이 고치는 순간이다.
  사실을 말하는 문장은 옮기는 순간 코드·설정·인용한 문서와 다시 대조한다. 원래 문서에 있던 문장이라고 맞는 것은 아니다.

## 일반어 검사

리뷰에서 지적받는 말의 절반은 한 원인이다. 코드 상수나 영어 개념어를 한자어 한 단어로 직역한 것.
활성(ACTIVE) · 불투명(opaque) · 가용(available) · 순번(auto increment) · 핫패스(hot path) · 실측(measured) · 스윕(sweep) · 슬라이스(slice).
저장소 안에서 굳은 말이라 쓰는 사람은 일반어로 착각한다. 판단 기준은 「맞는 말인가」가 아니라 **「보통 사람이 그 뜻으로 쓰는 말인가」**다.

- **직역 한자어를 쓰지 않는다.** 사람이 부르는 말로 푼다(활성 → 판매 중, 불투명한 → 추측할 수 없는, 순번 → 순서대로 증가하는 숫자).
  그 분야 용어라 바꿀 수 없으면 첫 등장에 정의한다(가용 → 판매 가능 수량, 실물에서 예약을 뺀 값).
- **검사 기준은 둘이다.** 템플릿 문서에서 본 말인가. 이 분야 밖 사람이 같은 뜻으로 쓰는 말인가. 둘 다 아니면 바꾼다.
- **업계에서 굳은 외래어는 순우리말로 바꾸지 않는다.** 기준은 그 일을 하는 다른 회사 사람도 그렇게 부르는가다. 저장소 안에서만 굳은 말과 다르다.
  로그 값을 `***` 로 바꾸는 일은 「마스킹」이다. 「가리기」로 바꾸면 그 일을 하는 사람이 쓰지 않는 말이 된다.
- **주어는 행위자, 서술어는 동사.** 사용자·서버·스케줄러·운영자가 무엇을 하는지 쓴다.
  대상을 주어에 세우고 동사를 빼서 「명사는 명사다」로 접지 않는다. 「핫딜은 여기서 예약한다」「추가 물량은 새 회차다」가 그런 문장이다.
  주어를 빼고 「Alloy 가 붙인 site 값이다」처럼 명사로 끝내지도 않는다. 무엇이 그 값인지 주어로 밝힌다.
  핫딜은 예약하지 않는다. 핫딜을 등록하면 서버가 재고를 예약한다.
- **초안을 쓴 뒤, `humanize-korean` 진단 전에 어휘 대조를 한다.** 도메인 명사·동사·한자어를 하나씩 위 기준으로 본다.
  진단은 쉼표와 리듬은 잡아도 이 단어들은 못 잡는다. 대조한 단어와 바꾼 것을 체크포인트 보고에 적는다.
- **리뷰에서 지적받은 표현은 먼저 해당 문서에서 고친다.** 여러 문서 형식과 다른 저장소에서도 반복될 원인을 찾았고 기존 규칙으로 설명할 수 없을 때만 전역 규칙으로 올린다.
  특정 도메인·형식에만 해당하면 저장소 규칙에 둔다. 지적받은 단어 하나가 아니라 그 단어가 지적받은 **원인**을 규칙으로 적는다.
- 독자가 개발자라면 일반어가 같은 발음의 개발 용어로 먼저 읽히지 않는지 확인한다. 뜻이 갈리면 「배치」를 「화면 배치」로 쓰듯 대상을 붙인다.
- `humanize-korean` 은 재작성기가 아니라 검사기다. **문서 하나를 끝내면 커밋 체크포인트 전에** 산문만 뽑아 진단을 받고 진단은 `humanize-korean` 스킬이 정한 사전 처리·요약 규칙·실행 경로를 그대로 따른다. 원문과 전체 분류 체계를 임의로 진단 에이전트에 넘기지 않는다.
  지적된 곳만 손본다. 재작성본을 되붙이지 않는다. 진단 결과(패턴·건수·고친 곳)를 체크포인트 보고에 적는다. 안 돌렸으면 안 돌렸다고 적는다.

## 코드를 실을 때

- **코드 흐름은 화살표 나열이 아니라 실제 코드에 가까운 의사코드로 적는다.** `payload ─fn→ DTO` 식 화살표는 실제 코드와 동떨어져 읽기 어렵다. 실제 메서드를 기준으로 타입·구조를 살리고, 타입을 변수 선언에 얹어 데이터 흐름을 코드 안에서 드러낸다. 짧은 메서드도 생략하지 않는다.
- **코드 블록은 전 곳 같은 방식으로 맞춘다.** 한 곳만 다르면 읽다가 눈이 멈춘다. 어느 클래스·흐름인지 헤더를 달고 주석에 목적을 함께 적는다. 한 곳을 고치면 나머지가 같은지 전수 확인한다.
- **도메인·타입 이름은 코드 식별자로 통일한다.** 한글로 섞지 않고(「파일 도메인」 ✗ → `File 도메인` ✓), 은어를 만들지 않는다.
- 긴 줄·주석은 잘리므로 폰트를 줄이거나 줄을 나눠 좌우 넘침 0 을 렌더로 확인한다. (색·폰트 등 구체값은 저장소 규칙)
- **독자가 그대로 따라 칠 쿼리·명령·설정 문자열은 실행해 보고 싣는다.** 로컬에 있는 도구나 컨테이너 이미지로 돌린다.
  문법이 맞아 보여도 그 도구가 거부하는 표기가 있다.
  읽기만 하는 명령과 일회용 환경에서 돌릴 수 있는 명령만 확인한다. 지우거나 배포하거나 운영 상태를 바꾸는 명령은 실행하지 않는다.
  실행하지 못했으면 그 사실을 문서에 적는다.

## 문체만 고칠 때 사실을 건드리지 않는다

- 코드 식별자·수치·경로·인용·각주·상호참조는 **원문 그대로** 둔다.
- 고친 뒤 원문과 **기계로 대조**해 이것들이 안 바뀌었는지 확인한다.
- 원문의 판단 기준과 조건을 보존한다. 더 자연스러운 말로 고치더라도 「이해」를 「설명」으로 바꾸는 것처럼 통과 기준이나 책임 범위를 바꾸지 않는다.

## 사용자와 함께 쓸 때

- **사용자가 「이 문장으로」 준 문장은 한 글자도 바꾸지 않는다.** 적용한 뒤 기존 문장이 남았는지, 요구한 표현이 다른 말로 바뀌지 않았는지 수정 전후를 대조한다. 바꾸고 싶으면 먼저 묻는다.
- 사용자가 설명으로 준 재료는 받아쓰지 않고 다듬되, 사실의 범위(대상·조건·빈도)는 넓히거나 좁히지 않는다. 더 나은 설명이 보이면 제안해 논의한다. 사용자가 고른 이름은 유지하고, 모호하면 문장 안에서 뜻을 밝힌다.

## HTML 로 쓸 때

- **HTML 요소와 CSS 로 정보의 관계를 드러낸다.** 핵심 결정은 요약, 비교는 표, 순서는 단계 흐름, 반복되는 결정은 카드, 긴 코드와 보충 근거는 `<details>` 를 쓸 수 있다. 마크다운 구조에 태그만 바꿔 붙이지 않는다.
- **핵심 결정과 선택 이유는 펼쳐 둔다.** 코드, 긴 근거, 드문 경계 조건만 접는다.
- **CSS 는 장식보다 정보의 위계와 묶음에 쓴다.** 색·그림자·애니메이션을 늘리기 전에 제목, 간격, 정렬, 그룹으로 관계를 보여준다.
- **같은 구조가 반복돼 읽는 흐름을 끊으면 더 단순한 형식으로 바꾼다.** 카드가 많으면 목록이나 표를 검토한다.
- **모바일에서도 정보 순서를 유지한다.** 여러 열은 한 열로 바꾸고, 표의 가로 스크롤은 페이지 전체가 아니라 표 영역 안에서만 생기게 한다. 가로 스크롤은 열 구조를 유지해야 하는 표에만 쓴다. 글이 많은 비교표는 좁은 화면에서 줄바꿈하거나 한 열 구조로 바꾼다.

## 슬라이드로 쓸 때

템플릿·토큰명·수치는 그 저장소 규칙에 있다. 여기엔 어느 저장소에서나 같은 것만 둔다.

- **소제목은 굵기가 아니라 색으로 구분한다.** 본문에도 굵게를 쓰므로 굵기만으로는 구분이 안 된다.
- **한글이 든 라벨에 `font-family:mono` 와 `text-transform:uppercase` 를 쓰지 않는다.** 소제목뿐 아니라
  eyebrow·kicker 처럼 작은 라벨도 대상이다. uppercase 는 한글에 효과가 없고 mono 는 한글을 폴백 글꼴로
  떨어뜨려 자간만 벌어진다. mono 는 코드 식별자만 따로 감싸 쓴다.
- **강조 장치는 위치가 아니라 뜻으로 쓴다.** 배경 반전·강조색은 그 장에서 가장 중요한 항목에만.
  "마지막이니까" 는 이유가 아니다.
- **항목이 짧고 서넛이면 카드가 아니라 가로 번호 행이다.** 카드는 문단이 여럿일 때 쓴다.
- **여백을 억지로 채우지 않는다.** `space-evenly` 로 요소를 벌려 빈칸을 감추는 것은 가독성이 아니다.
  남는 공간은 그대로 두거나 구조를 바꾼다.
- **클릭 넘김이 드래그를 막지 않게 한다.** 좌우 클릭으로 장을 넘기는 스크립트는 `mousedown` 좌표를
  기억해 6px 넘게 움직였거나 `window.getSelection()` 이 비어 있지 않으면 넘기지 않는다.
  이게 없으면 코드 블록을 드래그해 복사하려 할 때마다 장이 넘어간다.
- **코드 블록에 색을 넣으면 IDE 색을 따른다.** IntelliJ 활성 스킴은
  `~/Library/Application Support/JetBrains/IntelliJIdea*/options/colors.scheme.xml` 이 가리키고,
  `.icls` 는 부분 저장이라 플러그인 원본(`plugins/*/lib/*.jar` 안 `themes/*.xml`)과 **합쳐야**
  실제 색이 나온다. 폰트·행간은 문서 값을 유지한다 — 슬라이드 타이포그래피가 따로 잡혀 있다.
- **윤문은 작성 후 별도로 한다.** HTML 태그가 섞인 채로 돌리면 마크업이 깨진다.
  문장 블록만 뽑아 `humanize-korean` 을 돌리고 결과를 되반영한다.

## 처음 읽는 독자로 확인한다

작성자는 대화 맥락을 알고 있어 문서에서 빠진 설명을 못 본다. 독자 테스트는 문서만 읽는 검토자에게 질문에 답하게 해 빠진 설명을 찾는 절차다. 문서를 새로 쓰거나 크게 고치면(추가·삭제 50줄 이상) 확정하거나 커밋하기 전에 독자 테스트를 돌린다.

- 검토자는 작성 대화·프로젝트 규칙·다른 문서를 보지 못해야 한다. 같은 작업 폴더에서 띄운 서브에이전트는 그 폴더의 `CLAUDE.md` 를 받고 시작하므로 쓰지 않는다. 문서 사본 하나만 둔 폴더를 작업 폴더로 해 Codex 새 작업(`task --fresh --cwd 사본폴더 --prompt-file 프롬프트`)으로 돌리고 작성 규칙을 적용하지 말고 독자로만 읽으라고 적는다.
- 사본 폴더 이름은 `reader-test-{문서 이름}` 으로 짓는다. 문서 이름은 확장자를 뺀 파일 이름이다. `stop-check.py` 는 폴더 이름의 문서 이름으로 어느 문서의 독자 테스트인지 가른다.
- 검토자에게 「쓰기 전에 캐묻는다」에서 정한 독자를 준다. 검토자가 제목과 첫 화면만 보고 질문을 먼저 적게 한 뒤, 계획·설계 문서면 같은 절의 질문을 더한다.
- 답마다 근거가 된 문서 문장을 인용하게 한다. 인용하지 못한 답은 문서만으로 답할 수 없는 질문으로 센다. 독자 기준으로 설명이 필요한데 설명 없이 나온 용어, 두 뜻으로 읽히는 문장, 서로 어긋나는 서술, 핵심 결론을 이해하려고 뒤 섹션부터 읽어야 하는 곳도 인용과 함께 받는다. 고쳐 쓴 문장은 받지 않는다.
- 지적은 원문·근거와 대조해 실제 결함만 고친다. 검토자의 추측·취향과 문서가 이미 설명한 항목은 반영하지 않는다. 결과는 참고 목록이며 문서 확정을 막지 않는다.
- 확인 순서는 독자 테스트 → Codex 교차 검증(대상이면) → 어휘 대조 → `humanize-korean` 진단 → 렌더 확인이다. 앞 단계에서 문장이 바뀌면 뒤 단계를 다시 확인한다. 렌더 확인에서 산문을 고치면 어휘 대조부터 다시 확인하고 의미나 범위가 바뀌면 독자 테스트부터 다시 확인한다.
- 체크포인트 보고에 못 답한 질문 수, 지적 수, 실제 결함 수와 고친 곳을 적는다. 질문에 모두 답했다고 해서 문서 전체가 읽기 쉽다고 결론 내리지 않는다.
- 현재 대화에서 고친 문서가 새 파일이거나 크게 바뀐 채 커밋에 들어가는데 마지막으로 고친 뒤 그 문서의 독자 테스트를 돌리지 않았으면 커밋 명령을 낼 때 `stop-check.py` 가 막는다. 훅은 결과가 아니라 실행 여부만 본다. 오류로 끝난 호출과, 백그라운드로 띄운 뒤 완료 알림을 받지 못한 호출은 돌리지 않은 것으로 본다.
- 독자 테스트를 돌리기 전에 `codex-cross-check` 「쓸 수 있는지 먼저 확인한다」대로 남은 사용량을 본다. 모자라면 그 절이 정한 대로 사용자에게 묻는다.
- Codex 를 쓸 수 없으면 서브에이전트로 대신하지 않는다. 그 사실과 확인하지 못한 범위를 알리고 사용자의 판단을 받는다. 사용자가 한 줄에 「독자 테스트 생략」이라고만 쓰면 그 요청에서는 건너뛴다.

## 실제 산출 형태로 확인한다

「작업 성향」의 「검증」을 문서에 적용한 것이다.

- 산출물은 사용자가 볼 **실제 형태·크기로 렌더**해 확인한다. 축소 미리보기로 통과를 판단하지 않는다 — 작은 창에서 멀쩡하던 것이 실제 화면에서 잘린다.
- 정해진 틀이면 내용이 잘리거나 **바닥에 딱 붙지 않는지** 전 장을 본다. 안 들어가면 글자를 줄이기 전에 쪼갠다. 가독성이 떨어지면 분량을 늘려도 되지만 남발하지 않는다.
- **하단 여백은 남기는 게 아니라 나눈다.** 「바닥에 딱 붙지 않게」가 바닥을 비워도 된다는 뜻은 아니다. 성긴 장은 내용을 키우거나 세로로 가운데 정렬해 여백을 위아래로 나눈다.
- **표 셀에 줄바꿈 금지(`nowrap`)를 남발하지 않는다.** 설명 칸이 `nowrap` 이면 열 폭을 넘겨 옆 칸과 겹친다. 짧은 칸만 `nowrap`, 설명 칸은 wrap.
- **좌우 2단 레이아웃은 「컬럼 밖으로 삐져나오는지」로 겹침을 잰다.** 자주 놓치는 실수다 — 표·코드 블록의 **자체 스크롤폭(`el.scrollWidth`)만 보면 못 잡는다.** `nowrap` 셀이 표를 제 칸보다 넓혀도 표 요소 자체는 넘침으로 안 잡히고, 넘친 부분이 옆 칸으로 삐져나와 글자가 겹친다. **컬럼(칸) 박스**의 `scrollWidth > clientWidth`(칸 밖으로 넘친 content)나 왼쪽 칸의 오른쪽 끝이 오른쪽 칸 왼쪽 끝을 넘는지(`getBoundingClientRect`)로 잰다. 겹치면 그 칸을 넓히거나(`1fr 1fr` → `1.32fr 1fr`) `nowrap` 을 풀거나 글자를 줄인다. (렌더 없는 CI 로는 못 봐서 이 검사는 렌더로만 한다)
- **슬라이드처럼 크기가 정해진 문서는 `~/.claude/skills/doc-writing/render-check.js` 로 잰다.** 장마다 넘침, 코드 블록 안 잘림,
  상자 테두리까지 잰 바닥 여백, 글자와 다른 요소의 겹침을 낸다. 화면 조작부처럼 장 밖에서 장 위에 떠 있는 요소와의 겹침도 본다.
  사용자가 볼 실제 크기와 좁은 패널 크기처럼 **두 크기 이상**에서 잰다. 기준 크기·선택자·바닥 여백 값은 저장소 규칙에 둔다.
  숨긴 장도 배치가 남아 있어야 잰다. 장을 `display:none` 으로 숨기는 문서는 한 장씩 보이게 하고 잰다.

  ```js
  const fs = await import("node:fs/promises");
  const os = await import("node:os");
  const code = await fs.readFile(`${os.homedir()}/.claude/skills/doc-writing/render-check.js`, "utf8");
  await page.cdp("Emulation.setDeviceMetricsOverride", { width: 1600, height: 900, deviceScaleFactor: 1, mobile: false });
  console.log(JSON.stringify(await page.evaluate(`(${code})({ slide: ".slide", body: ".body", minBottom: 20 })`), null, 1));
  ```

- 이미 정해진 템플릿·형식은 **요구가 있을 때, 요구된 부분만** 바꾼다.
- 확인한 것을 항목별로 보고한다.

## 공개 저장소 문서를 따로 배포할 때

- 공개 저장소의 문서를 저장소와 따로 배포하면, 독자가 보던 페이지와 위치로 돌아갈 수 있게 한다. 링크 위치와 뒤로 가기 조건·대체 주소는 저장소 템플릿에 둔다.

## 대량 편집은 백업하고 자체 검증한다

- 번호 재매김·일괄 치환 같은 기계 편집은 **먼저 백업**하고, 결과를 스크립트로 검증한 뒤 신뢰한다 — 정규식 하나가 조용히 옆엣것을 오손한다.
- 구조를 바꾸면 번호·상호참조·목차가 어긋나지 않았는지 전수 확인한다.

## 결정 이력과 검증 사례

「대화의 흔적을 문서에 옮기지 않는다」는 그대로다. 논쟁을 재현한 방어 문단은 그 논쟁을 모르는 독자에게 뜬금없다. 다만 **결과**는 정해진 자리에 정해진 형식으로 남긴다.

- **「바뀐 결정」 표는 저장소 규칙이 두라고 정한 저장소에서만 문서 끝에 둔다.** 열은 날짜 · 이전 · 이후 · PR 댓글 링크이고 한 줄이 한 번의 번복이다. 과정은 적지 않는다. 타임라인은 PR 에 있다.
  정하지 않은 저장소에서는 번복을 문서에 적지 않는다. 그 기록은 PR 댓글과 커밋 「검토:」 줄에 남는다.
- 계획 문서를 구현 뒤에 갱신하면 정한 것·지금 상태·완료 결과를 문장 시제에 맡기지 않고 제목이나 라벨로 구분한다. 처음 추정과 나중 결과를 한 표에 두면 기준일을 적는다.
- **검증 사례는 PR 댓글과 커밋의 `검토:` 줄에서만 가져온다.** 기록에 없는 주체(「사람이 잡았다」·「AI 가 제안했다」)는 적지 않는다. 기록 이전의 사례는 「누가 무엇을 했나」를 사용자에게 한 번 묻고 답을 그대로 받아 적는다. AI 가 지어 쓰면 포장이 되고 면접에서 드러난다.

## AI 협업 문서

포트폴리오 저장소에는 AI 와 어떻게 일했는지를 설명하는 문서 한 편을 둔다. 규칙을 복제하는 문서가 아니라 검토자가 검증 흔적을 따라갈 수 있게 하는 문서다. README 에는 이 문서로 가는 한 줄만 둔다.

섹션 순서는 ADR 골격을 따른다.

1. 요약 3줄 — 역할 분담 / 검증이 몇 겹인지 / 흔적이 어디 있는지
2. 문서를 먼저 쓰게 하는 이유 — AI 가 어떤 의도로 만들려는지 문서로 먼저 읽고, 이해하지 못한 것은 구현으로 넘어가지 않는다는 것
3. 역할·검증·흔적 표 — 단계마다 「AI 가 하는 것 / 사람이 하는 것 / 근거가 되는 설정 / 흔적이 남는 곳」
4. 검증 사례 하나 — 위 「검증 사례」 규칙대로 기록에서만
5. 경계 — 산문은 AI 가 쓴다는 것, 대화 기록은 공개하지 않는다는 것, 전역 규칙은 저장소 밖에 있다는 것을 담백하게
6. 규칙 파일 위치 — 링크만

AI 활용을 자랑하는 문서가 되면 안 된다. 보여줄 것은 규칙의 양이 아니라 검증이 돌았다는 증거다.

문서마다 AI 작성 표기를 달지 않는다. 경계는 README·AI 협업 문서 한 곳에만 둔다.
