# 블로그·회고 글

velog 같은 공개 블로그에 올리는 기술 글의 규칙이다. `SKILL.md` 의 전역 규칙 위에 적용한다.
2026-10-22 재전송 글 리뷰에서 확정했고 2026-10-23 마일리지 글, 2026-10-26 연동 규격 글, 2026-10-27 구조 글 리뷰를 반영했다. 글마다 리뷰가 쌓이면 갱신한다.
저장소 경로·그림 폴더·렌더 방법 같은 구체값은 그 저장소의 `CLAUDE.md` 에 둔다.

## 독자

이력서 링크를 타고 온 CTO·시니어 개발자가 첫째 독자이고 velog 일반 독자가 둘째다.
둘이 충돌하면 증거와 결정을 우선하고, 서사는 도입과 소제목에서 살린다.

## 문체

- 본문은 습니다체다. 제목·소제목·결과 줄·표·그림 라벨에는 종결 어미를 쓰지 않는다.
- 설계와 구현의 이유는 글쓴이가 결정한 일로 과거형으로 쓴다. 「~ 때문에 JDBC batch insert 를 사용했습니다」처럼 쓰고 「~해야 합니다」 같은 당위 표현으로 일반 규칙처럼 쓰지 않는다. 코드가 지금 하는 동작을 설명할 때만 현재형을 쓴다.
- 아직 하지 않은 일의 효과와 필요성은 글쓴이의 생각으로 쓴다(「~것 같다는 생각을 가지고 있습니다」「~할 것 같습니다」). 「판단합니다」나 단정형으로 쓰지 않는다.
- 업무 행위의 구어 동사 금지는 비즈니스 문체와 같다(「문서 종류에 맞춘 목소리」 대응표). 전송·조회·확인·실행·기록으로 작성한다.
- 「끊기다」는 「단절」로, 「문의」는 「민원」처럼 그 현장에서 실제로 사용하는 말을 쓴다. 본문과 그림 라벨이 같은 낱말을 쓴다.
- 「저희」「우리」 대신 주어를 대상으로 쓴다.
- 독자가 모를 도메인 용어는 첫 등장에 괄호로 한 번 푼다. 「마일리지(세대별 무료 주차 시간)」.
- 개발자 독자 글은 협업에서 통용되는 개발 용어(파라미터, 테스트 코드, 영속 상태, flush, batch insert)를 그대로 쓴다. 일반어 검사와 업무 동사 대응표는 이 용어를 풀어 쓰는 근거가 아니다. 글쓴이와 팀이 실제로 쓰지 않는 신조어는 쓰지 않는다(「피처 플래그」 대신 「기능 사용 여부」).
- 개수는 아라비아 숫자와 단위로 쓴다(5개의 API, 4개의 호출부). 「한 곳」「한 번」「하나」「한 구간」「한 건마다 한 번」 같은 관용 표현은 그대로 둔다.

## 구성

1. 제목: 종결 어미 없이 짧고 구체적으로. 「사라진 출차 기록 찾기: 단지 네트워크 단절과 재전송 구조」처럼 주제 + 콜론 + 설명, 또는 레퍼런스처럼 구어·반전.
2. 도입: 장면으로 시작한다(민원 요지 인용, 대화, 질문). 메타 설명 문단은 없고 「이 글은 … 과정을 기록한 회고입니다」 한 문장만 도입 끝에 둔다. 자기소개는 없다.
   장면은 실제 사실로 쓴다. AI 가 재구성한 장면은 쓰지 않고 글쓴이에게 확인한다.
3. 결론 먼저: 도입 바로 뒤 `## 결론 먼저` 아래 문제·원인·해결·결과 카드 그림 한 장. 그림 아래 글 요약은 두지 않는다.
4. 본문 순서: 문제 장면 → 원인 탐색 → 대안 검토(제약은 인용 블록, 대안은 표) → 결정과 구현(흐름도, 필요하면 가명 의사 코드) → 결과 사례 → 결말.
   제약 인용 블록에는 선택지를 실제로 가른 조건만 둔다. 팀 규모처럼 어느 결정에나 해당하는 사정은 제약으로 세우지 않는다. 제약은 그 제약을 겪은 사례보다 기능이 무엇을 허용하는지로 쓴다.
5. 소제목: 구어·구체(「그냥 클라우드 서버가 직접 받으면 안 되나요」「두 번 와도, 순서가 바뀌어도」). 독립된 결정 여럿은 `### 1.` 처럼 짧은 주장 소제목이고 긴 설명은 본문 첫 문장으로 내린다. `###` 소제목은 그 위 `##` 제목의 주장을 나눈 것만 둔다. 제목과 관계없는 내용은 `##` 로 올린다.
6. 결말: 대안을 돌아보면 「다른 방법은 없었을까」, 남은 일을 정리하면 「남은 일」로 끝낸다. 제목과 내용이 맞아야 한다. 글 끝 정리 절은 없다.
   남은 일에는 앞으로 할 일만 쓴다. 지금 코드에 남은 규칙 위반은 쓸 이득이 없으므로 쓰지 않는다.
7. 글자 수 목표는 없다. 레퍼런스 수치는 증거(그림·코드·표)가 빠졌는지 의심하는 신호로만 쓴다.

## velog 제약

- 목록 항목 안에 제목을 넣지 않는다. 렌더가 어색하다.
- 다이어그램 문법(mermaid 등)은 렌더되지 않는다. 그림은 이미지로 올린다.
- 문단 안에서는 문장마다 줄을 바꾼다. 같은 문단 안 줄바꿈은 줄 끝 공백 두 칸이고 빈 줄은 문단을 나눈다. 전역 규칙의 「온점마다 줄을 바꾸지 않는다」보다 이 규칙이 우선한다.
- 인용 블록(`>`)은 왼쪽 세로선이 있는 상자로 렌더돼 카드처럼 보인다. 주장 + 설명 묶음에 쓴다.
- 표에 행 색을 쓰지 않는다. 대안 표의 채택 행은 모든 칸을 굵게 쓴다.
- 다크 모드에서 이미지는 그대로 표시된다. 흰 배경 PNG 는 검은 화면 위 흰 직사각형이 된다.

## 그림

- 글마다 구조·흐름·상태 그림 2~3장과 결론 카드 1장이다. 실제 화면 사진은 넣지 않고 같은 스타일로 그린다.
- 스타일 기준은 한국 기술 블로그(토스 기술 블로그)다. 흰 카드, 옅은 회색 영역 묶음, 강조색 하나(파랑), 실패·단절은 보조색 하나(주황), 한글 글꼴(Pretendard). 장식 격자·아이소메트릭·그라데이션은 쓰지 않는다.
- 캔버스는 글이 표시되는 폭과 같게 그린다. velog 본문은 768px 이므로 캔버스 폭 800 으로 그리고 2배 해상도(1600px) PNG 로 렌더한다. 1600 캔버스에 그리면 표시될 때 절반 이하로 줄어 글자를 읽을 수 없다. 글자 크기는 노드 이름 18px, 설명·라벨 13~14px 로 본문(18px)에 가깝게 둔다. 세 칸이 가로로 안 들어가면 세로 흐름으로 바꾼다.
- 다크 모드 대응으로 투명 배경 위에 테두리 있는 흰 카드로 그린다.
- 결론 카드는 카드 넷(문제·원인·해결·결과)을 2×2 로 두고 결과 카드만 강조색이다. 모든 그림에 제목·부제를 넣지 않는다. 절 제목이 그 역할을 한다.
- 영역 이름과 노드 이름은 본문과 같은 낱말이다. 한 그림에 노드 아홉 개 안, 노드 이름은 세 어절 안, 설명 줄은 한 줄.
- 각주로 그림에 없는 뜻풀이를 둔다(「화면 문구의 주차 서버는 단지의 경비원 서버입니다」).
- 그림도 SVG 를 텍스트로 읽는 독자 테스트와 교차 검증을 거친다.

## 증거

- 이력서에 이미 쓴 수치는 블로그에도 쓴다. 이력서를 본 회사가 글을 읽으므로 둘이 어긋나면 안 된다.
- 업체 실명·날짜·내부 경로·인증 방식은 쓰지 않는다.
- 사내 프로젝트 코드명(저장소 이름)은 쓰지 않고 그 서버가 하는 일로 부른다. 「face-gate」는 이력서와 같이 「안면인식 출입 서버」로 쓴다.
- 코드는 그림이 보여 주지 못하는 것을 보여 줄 때만 둔다. 그림과 같은 내용이면 흐름도로 바꾼다(글마다 0~2개, 10~20줄). 실제 코드를 확인한 뒤 가명 의사 코드로 작성한다(「코드를 실을 때」).
- 의사 코드도 실제 코드처럼 읽혀야 한다. 줄 끝 주석으로 식을 끊지 않고 주석은 그 줄 위에 둔다. 한 줄 if-return 같은 축약을 쓰지 않는다.
- 의사 코드는 실제 코드의 호출 순서와 결과를 유지한다. 글이 설명하는 설계와 어긋나는 세부(조건을 둔 계층 등)는 설계대로 정리해도 된다. 독자는 실제 코드를 볼 수 없다.
- 설계 수치(주기·건수·상한)는 공개한다.
- 출처 링크는 글쓴이가 아는 것만 넣는다. 후보와 요지를 먼저 제시한다.

## 작업 절차

1. 레퍼런스 분석(매체가 바뀌었거나 분석이 오래됐을 때) → 독자·문체·구성 계획 → 사용자 승인.
2. 사실 확인: 글쓴이만 아는 것은 질문, 코드로 알 수 있는 것은 코드로 확인. 사례 정리 파일이 있으면 그 파일이 사실의 정본이고 확인한 사실은 그 파일에 기록한다.
   결정을 다루는 절은 쓰기 전에 그 결정의 실제 이유, 검토한 대안, 버린 이유를 글쓴이에게 질문한다. 사례 정리 파일의 한 줄 이유를 그대로 쓰지 않는다.
   사례 정리 파일의 결정 목록을 그대로 질문 목록으로 사용하지 않는다. 항목마다 글의 주제와 관계있는지 먼저 판단하고 관계없는 항목은 질문하지 않고 글에서 뺀다.
   코드로 확인하는 범위는 작업 지시가 지정한 저장소다. 지정 범위 밖 저장소(옛 버전 코드 등)를 글의 근거로 삼지 않는다. 필요해 보이면 먼저 질문한다.
3. 작성 → 그림 → 독자 테스트(전체 한 번, 그 뒤 정보가 바뀐 곳만) → Codex 교차 검증 → 어휘 대조 → `humanize-korean` 진단 → 렌더 확인.
4. 리뷰용 문서에 글과 그림을 올리고 사용자가 리뷰한다. 사용자가 직접 고친 판이 정본이다.
5. 리뷰 지적은 「규칙에 없어서」와 「규칙을 어겨서」로 가른다. 전자는 이 파일이나 `SKILL.md` 에 추가한다.
