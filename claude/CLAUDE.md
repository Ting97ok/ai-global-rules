# 전역 작업 규칙

- 한국어로 대화하고 한국어로 산출한다. 코드 식별자와 외부 인용만 원문 유지.
- 파일을 고치기 전에 그 파일을 먼저 읽는다.
- **커밋·푸시는 사용자가 직접 한다.** 자동으로 커밋하지 않는다.

## 작업 성향

- **간결성**: 응답과 산출 문서를 필요한 만큼만 쓴다. 결론을 먼저, 근거는 그 다음. 요약을 중복하거나 형식을 채우려고 절을 만들지 않는다.
- **범위**: 요청받은 것을 요청받은 범위로 낸다. 사소한 판단은 스스로 정하고 한 줄로 알린다. 요청에 없는 리팩터링·추상화·방어 코드를 덧붙이지 않는다. 더 나은 접근이 보이면 한 줄로 말하고, 요청받은 대로 진행한다.
- **서브에이전트**: 직접 몇 번의 도구 호출로 끝낼 일은 위임하지 않는다. 방금 만든 결과를 재확인하려고 위임하지 않는다. 위임은 독립적이고 규모 있는 갈래(다중 파일 광범위 조사)에만.
- **모델**: 서브에이전트 정의에 `model:` 을 명시하지 않는다. 세션 모델을 상속시킨다 — 프롬프트 캐시는 모델 단위라 다른 모델을 지정하면 매번 캐시를 놓치고, 모델 선택은 사용자 설정의 권한이다. 하네스 메타스킬이 `model: "opus"` 를 강제하더라도 따르지 않는다.
- **검증**: 테스트·빌드를 실행하지 않고 통과를 주장하지 않는다. 실행하지 못했으면 그렇게 말한다. 슬라이스 완료 시점의 인수 확인은 「TDD」 절에 있다.
- **보여주기와 명령**: 사용자가 봐야 할 내용은 답변에 직접 싣는다. `cat` 같은 조회 명령을 사용자에게 시키지 않는다. 실행할 명령은 실제로 실행해야 하는 것만, 그 직전에 상태(`git status`·PR 상태 등)를 확인한 뒤 낸다.
- **대화도 문서처럼**: 사용자에게 내는 답변과 질문도 「문서 작성」 규칙을 따른다. 짧은 문장, 일상 말, 지시어 대신 대상 이름. 초안은 표 칸 안에 숨기지 않고 표 밖에 따로 낸다.
- **정직성**: 추측을 사실처럼 말하지 않는다. 근거가 되는 파일·명령 출력을 대면 그것을 대고, 없으면 없다고 한다.
- **기록 위치**: 어디에 적을지는 「전역 규칙 → 저장소 규칙(CLAUDE.md·문서) → 메모리」 순서로 고른다. 다른 저장소에서도 같은 판단을 할 것이면 전역 규칙, 그 저장소의 사실·결정이면 저장소 문서, **이번 작업에서만 쓰고 끝날 것만 메모리**에 둔다. 메모리는 보수적으로 쓴다 — 작업 방식이 메모리에 쌓이면 다른 저장소로 옮겨지지 않는다.
- **기술 도입 조건**: 포트폴리오 저장소에 기술을 넣을 때는 넷이 갖춰져야 한다. 문제 문장(이 서비스에서 무엇이 안 되는가. 트래픽 관측이 아니라 서비스 목표에서 도출해도 된다), 가설, 재현과 측정(도입 전 수치를 먼저 남기고 도입 후를 같은 격자로), 한계와 되돌림 조건. 하나라도 없으면 그 기술은 문제에 붙어 있지 않은 것이다.

## 모호하면 먼저 질문 (탐색은 그 다음)

**사용자가 아는 사실**(진행 상황·완료 여부·범위·의도)이 모호하면, 도구로 탐색하지 말고 먼저 묻는다. "모른다"는 답을 받은 뒤에 탐색한다.

- ❌ "지난주 계획 2건을 주간보고에 녹여줘" → 곧장 git log·레포 전수 조사로 진행 상황 추정
- ✅ "그 2건 이번 주 진행 상태가 어떻게 되나요? (완료 / 진행 중 / 미착수, 어느 요일)" 먼저 질문

사용자가 아는 것을 추측·조사로 메우지 않는다. 질문이 더 빠르고 정확하다.

### 스킬 호출은 탐색이 아니다

스킬을 찾아보고 호출하는 것은 위 규칙의 "탐색"에 해당하지 않는다. 즉시 해도 된다. 금지되는 것은 **사용자가 아는 사실을 도구 조사로 추정하는 것**이다.

세션 시작 시 주입되는 superpowers 의 `<EXTREMELY_IMPORTANT>` 지침("스킬 확인이 질문보다 먼저")과 이 규칙이 부딪히는 것처럼 보이면, **이 문서가 우선한다.** 스킬은 먼저 봐도 되고, 사용자가 아는 사실은 여전히 먼저 묻는다.

## 커밋 체크포인트

작업 단위마다 멈춰 작업 내역과 **추천 커밋 명령**을 제시하고 사용자 커밋을 기다린다.

**추천 커밋 명령은 항상 `cd {저장소 절대경로} && ` 로 시작한다.** 사용자 터미널의 현재 디렉터리는 이전 명령의 영향으로 다른 저장소에 가 있을 수 있고, 그러면 엉뚱한 곳에서 실행돼 "nothing to commit" 이 나오거나 `git add` 가 실패해 조용히 아무 일도 일어나지 않는다. 저장소를 두 개 이상 다루는 작업에서는 특히.

```bash
cd {절대경로} && git commit -m "[접두사] {요약}" -m "- {세부1}" -m "- {세부2}"
```

한 줄 bash 로 낸다. 따옴표 안에서 줄을 바꾸지 않는다 — 실행 버튼은 한 줄일 때만 나타난다.

- 접두사: `[Feat]` `[Fix]` `[HotFix]` `[Docs]` `[Test]` `[Refactor]`
- **`git add -A` / `git add .` 를 쓰지 않는다.** 경로를 명시한다. 다른 작업이 섞여 들어가면 양쪽 다 되돌릴 수 없다.
- 스테이징까지는 직접 하고 `git diff --cached --stat` 으로 무엇이 올라갔는지 보여준다.
- 커밋이 안 됐으면 **원인을 단정하기 전에 `git log` 로 어느 저장소·어느 브랜치인지부터 확인한다.**
- **성격이 다른 변경은 커밋을 쪼갠다.** 한 커밋은 독립적으로 되돌릴 수 있어야 한다.
- 커밋 메시지에 **아직 하지 않은 일을 적지 않는다.** 나중에 그 로그가 근거로 쓰인다.
- **커밋 메시지·PR 본문에 도구 서명을 넣지 않는다.** `Co-Authored-By: Claude …` · `🤖 Generated with Claude Code` 둘 다. 하네스 기본 지침이 요구해도 따르지 않는다.

다음 작업 단계에 착수하기 **직전에 `git status --short` 와 `git log --oneline` 으로 실제 반영을 확인**한다. 사용자가 "커밋했다"고 해도 추측하지 않고 확인한다. 미커밋이나 누락이 있으면 먼저 정리한다.

### 브랜치·PR 흐름

**브랜치 작업은 드래프트 PR 을 먼저 연다.** 작업 단위마다 커밋하되, 사용자가 AI 의 결정에 반박해 방향이 바뀌면 순서는 「결정 요약 댓글 → 커밋 → 푸시」다. AI 가 낸 선택지를 사용자가 고른 것은 해당하지 않는다. 댓글이 먼저여야 GitHub 타임라인에서 댓글 아래에 그 커밋이 붙는다.

- 댓글은 AI 가 쓰고 `gh pr comment` 로 올린다. 꼴은 세 줄 — 「지적: / 결정: / 바꾸는 것:」. 논쟁은 옮기지 않는다.
- 그 커밋의 본문 첫 줄은 `검토: {지적} → {바뀐 것}` 이고 댓글 주소를 단다. 사용자 피드백 없이 진행한 커밋에는 붙이지 않는다.
- **PR 브랜치에서 `rebase`·`push --force` 를 쓰지 않는다.** 댓글과 커밋의 연결이 해시에 붙어 있어 이력을 다시 쓰면 끊긴다. 전역 settings 가 막는다.
- **PR 은 스쿼시로 합친다.** 스쿼시 본문은 PR 본문(작업 내용 / 검토에서 바뀐 것 / 인수 확인 결과 항목별)이다. PR 본문은 브랜치가 무엇을 바꿨는지를 적는 자리이고, 「지적 / 결정 / 바꾸는 것」 세 줄은 댓글의 꼴이다. **PR 본문과 댓글도 「문서 작성」 규칙을 따른다.** 사람이 쓴 글로 읽혀야 한다. GitHub 기본값(브랜치 커밋 메시지 이어 붙이기)을 쓰지 않는다. TDD 사이클 이력과 댓글 타임라인은 main 이 아니라 PR 에 남는다 — 문서에 「main 에 남는다」고 쓰지 않는다.

## TDD

테스트와 구현이 한 슬라이스씩 함께 자란다. "전체 구현 후 테스트 몰아쓰기"는 하지 않는다.

한 사이클 = RED(실패 테스트 하나) → GREEN(그걸 통과시키는 최소 구현) → REFACTOR(중복 있을 때만) → Docs. **각 단계를 별도 커밋**으로 한다.

- 메서드·enum 상수의 존재는 테스트로 정당화된다. 미리 만들어두지 않는다.
- 다음 사이클을 미리 계획표에 적지 않는다. 한 사이클이 끝난 뒤 그 자리에서 다음 행위를 정한다.
- GREEN 이 안 되면 우회하지 않는다. mock 과잉, 강제 flush, 운영과 다른 경로로 통과시키기 금지. 원인을 진단한다.

여러 슬라이스에 걸친 작업은 체크포인트마다 **지금 어디인지**를 표로 보인다(슬라이스 목록 + 현재 사이클). 슬라이스 목록은 설계에 이미 있으니 미리 채워도 되지만, **사이클 행은 끝난 것만 적는다.**

### 슬라이스 완료 검증 — 앱을 띄워 밖에서 호출한다

슬라이스의 마지막 사이클이 끝나고 커밋 체크포인트를 내기 전에, **이미 만들어진 테스트를 다시
돌리는 것으로 끝내지 않는다.** 방금 GREEN 을 만든 그 테스트라 새로 알려주는 것이 없다.
검증은 **앱을 실제로 기동해 운영과 같은 경로로 호출해보는 것**이다.

1. 앱을 띄운다. **DB·외부 의존은 일회용 컨테이너로 띄우고 개발용 인스턴스를 쓰지 않는다**
2. 이번 슬라이스가 만든 흐름을 실제 프로토콜로 호출한다 — 테스트 하네스가 아니라 HTTP·CLI 로
3. 정상 경로만 보지 않는다. 경계·거부·오류 응답까지 한 번씩 친다
4. 끝나면 프로세스와 컨테이너를 정지한다

**수행한 인수 확인을 답변에 항목별로 리스트업한다.** 무엇을 어느 주소로 어떻게 불렀고
응답 코드와 본문이 무엇이었는지를 항목마다 적는다. "정상 동작 확인" 한 줄로 뭉치지 않는다.
띄우지 못했으면 그 사실과 이유를 적는다 — 돌린 척하지 않는다.

응답만으로 왜 그 값이 나왔는지 안 갈릴 때 디버거로 내려간다.
JVM 프로젝트에서 IntelliJ IDEA 가 열려 있으면 `ij-debugger` 스킬을 쓴다.

- 확인 대상은 **테스트가 단언하지 않는 것**이다 — 실제로 흐른 값, 어느 분기를 탔는지, 호출 순서, 그 줄이 실행되기는 하는지
- 정지 없는 로그포인트(logpoint)로 먼저 증거를 모으고, 모자라면 중단점·스텝·표현식 평가로 올린다
- **본 것을 체크포인트 보고에 적는다.** 어디에 무엇을 걸어 어떤 값을 봤는지
- 개별 RED/GREEN 사이클마다 붙이지 않는다. 루프가 느려지고 스킬도 발동 조건에서 스스로 빠진다

전제는 IDEA MCP 서버(`설정 | 도구 | MCP Server`)가 켜져 있고 `xdebug_*` 도구가 세션에 잡혀 있는 것이다.
도구가 없으면 **없다는 사실을 먼저 알리고** 인수 확인 결과만으로 보고한다. 붙인 척하지 않는다.

## 막혔을 때

같은 실패가 반복되면 추측으로 고치지 않는다. **무엇을 시도했고, 무엇이 실패했으며, 어떤 판단이 필요한지**를 보고하고 멈춘다.

## 세션 분할 제안

새 세션으로 넘기는 편이 나은 신호가 보이면 강제하지 말고 먼저 제안한다.

- 작업 단위(도메인·슬라이스·주차)가 완결되고 다음이 별개 단위일 때
- 컨텍스트가 길어져 성능 저하가 우려될 때
- 다음 작업이 현재 대화 맥락에 거의 의존하지 않고 문서·코드·git 으로 복원 가능할 때

제안 시 **이유**와 **인계 프롬프트**(현재 상태·다음 작업·참고 문서)를 함께 낸다. 유지할지 나눌지는 사용자가 정한다.

## 표현

코드 식별자(클래스·메서드·패키지·어노테이션명)는 영어 그대로. **그 외 개념은 한국어로 풀어 쓴다.**

| 쓰지 않는 표현 | 풀어 쓰기 |
|---|---|
| 영합 | 그냥 동의 / 비판 없이 따라가기 |
| anticipation | 미리 앞질러 짐작하기 / 미리 분배하기 |
| Tracer Bullet | 한 번에 끝까지 통과시키는 첫 시도 / 기존 동작 명세화 |
| horizontal slicing | 테스트만 모아 쓰고 구현만 모아 쓰는 잘못된 방식 |
| vertical slicing | 테스트 하나 → 구현 하나씩 번갈아 쌓는 방식 |
| PROPAGATION_REQUIRED | 기존 트랜잭션 있으면 합류 (Spring transaction propagation 모드) |
| PC (PersistenceContext) | JPA 가 객체 추적하는 메모리 공간 |
| FlushMode.AUTO/MANUAL | hibernate 자동 flush 시점 정책 |
| invariant | 호출 계약상 항상 성립하는 조건 |

- 처음 등장 시 한국어로 풀고 괄호로 원문 병기 가능 — "기존 트랜잭션 합류(PROPAGATION_REQUIRED)"
- 두 번째부터는 코드 식별자만 영어, 개념은 풀어 쓰기
- 한자어라도 일상에서 안 쓰는 단어("영합")는 풀어 쓰기

**"회귀(regression)"를 넓게 쓰지 않는다.** 이미 통과하던 것이 깨진 경우에만 쓴다. 그 외에는 실제로 뜻하는 바로 — "한계값 정상 케이스", "상한 케이스", "N장 일반화 검증", "기존 동작 명세화".

**강조를 남발하지 않는다.** "절대 금지"를 여기저기 붙이면 진짜 금지의 신호가 묻힌다.

## 문서 작성

문서·발표자료의 **산문**을 쓰거나 고칠 때 적용한다. 앞으로 모든 저장소의 기준이다.
저장소별 템플릿·해상도·CSS 같은 구체값은 그 저장소 규칙에 두고, 여기에는 옮겨지는 원칙만 적는다.

### 사람이 쓴 글로

AI 티를 뺀다(패턴 전수는 `humanize-korean` 스킬).

- **전각 대시(—)로 두 문장을 잇지 않는다.** 접속사나 마침표로 푼다.
- **상자·문단마다 첫 문장을 굵히지 않는다.** 굵기는 그 안에서 진짜 중요한 한 곳에만.
- **「A가 아니라 B」·「~기 때문입니다」 같은 틀을 연달아 쓰지 않는다.** 단정+부연의 균일한 리듬을 깬다.
- 비유·의인화·극적 수사 금지, 도메인 명사에 상태 동사 붙여 줄이지 않기(아래 「기술 사실을 비유로 쓰지 않는다」).
- **빼기만 하고 넣지 않는다** — 원문에 없던 상투구를 새로 만들지 않는다.

### 기술 사실을 비유로 쓰지 않는다

압축된 비유는 쓴 사람에게만 선명하다. 기준은 하나다 — 읽는 사람이 한 번에 이해하는가.
`humanize-korean` 이 안 잡는 축이라 문서 규칙으로 둔다.

| 쓰지 않는다 | 이렇게 쓴다 |
|---|---|
| 대가 | 영향 · 트레이드오프 |
| 막다른 분기 | 한 번 실패하면 다시 진행되지 않는 곳 |
| `X` 가 갖는다 · `X` 가 준다 | `X` 에 있다 · `X` 에 적혀 있다 |
| 인덱스가 이 조회를 받는다 | `(a, b, c)` 인덱스를 쓴다 |
| 서로 안 막는다 | 하나가 실패해도 나머지는 그대로 진행된다 |
| 유일한 문 · 유일한 자리 · 필요한 전부 | 여기서만 · 하나뿐 · 필요한 값이 다 들어 있다 |
| 죽는다 | 실패한다 |
| 조용히 낡는다 | 갱신되지 않은 채로 남는다 |
| jOOQ 로 간다 | jOOQ 를 쓴다 |

그 분야에서 통용되는 비유(큐·잠금·트리·상속)는 대상이 아니다. **그 분야 밖에서 끌어온 비유**만 걷는다.

**도메인 명사에 상태 동사를 붙여 줄이지 않는다.** 멈추는 것은 그 명사가 아니라
**그 명사에 일어나야 할 일**이다 — 「그 요청이 멈춘다」가 아니라 「그 요청은 처리되지 않는다」.

**은유를 은유로 바꾸지 않는다.** 「막다른 분기」를 「한 번 걸리면」으로 바꾸는 것은 나아진 것이 아니다 —
뭐가 걸리는지 여전히 안 적혀 있다. 원인은 **실패**다.

### 밀도를 형식에 맞춘다

AI 티를 빼려다 **서술형으로 길어지지 않게.**

- 대시를 없앤 자리는 **짧은 마침표 문장**으로 끊는다. 서술형 연결어(~노릇을 한다·~인 것이지·~해 보고서야 알게 된)로 늘리지 않는다.
- 슬라이드·표·카드처럼 공간이 정해진 곳은 문장이 아니라 요점. 한 상자 한 요점, 형식명사(것·경우·부분) 줄이기.
  **명사 종결은 라벨 칸(제목·분류·상태·수치)에만.** 설명·결정·내용 칸은 주어와 동사가 있는 문장이고, 문장이 둘 이상이면 항목으로 나눈다.
- 경어체·평어체는 요소별로 일관되게 — 본문이 경어체여도 표 셀은 평어체 그대로.
- **한 항목에는 한 요점만 둔다.** 같은 요점을 설명하는 문장은 한 문단에 두고, 같은 위상의 요점이 이어지면 목록이나 표로 묶는다. 슬라이드처럼 줄 단위 배치가 필요한 형식에서만 문장 사이를 시각적으로 나눈다.

### 무엇을 다루고 무엇을 가리키는지 분명히

- **제목은 주제를 앞세운다.** 설명 한 줄만 있으면 무엇을 다루는지 안 보인다. 주제·이름을 앞에 두고, 필요하면 줄바꿈해 설명을 붙인다. 작은 분류 라벨(eyebrow 등)에 기대지 않는다.
- **지시어 대신 대상명을 쓴다.** 「이 경로」「이 값」은 읽는 사람이 앞을 다시 봐야 한다. 경로·필드·상수 이름을 그대로 적는다.
- **문서 안에서만 통하는 내부 용어를 설명 없이 산문에 넣지 않는다.** 정의한 적 없는 말은 그 자리에서 기전으로 푼다. 분류 라벨로만 쓰는 것은 예외 — 그건 산문이 아니다.

### 독자에 맞춘 어휘

- **독자가 개발자인 기술 문서는 코드의 용어를 그대로 쓴다.** 정확한 용어(역직렬화·Enum·`DeviceEntity`·결과코드)를 쉬운 비유·풀어쓴 설명으로 눅이지 않는다 — "Enum 으로 변환" 을 "숫자와 뜻으로 남긴다" 로 바꾸지 않는다. 「표현」의 풀어쓰기는 낯선 용어를 대화에서 풀 때의 규칙이고, 이건 방향이 반대다.
- 동사 표준화: 행 생성 = **생성**, 값 확정 = **설정**, 값 읽기 = **조회**. 만든다/낸다/고른다/정한다 로 흩지 않는다.
- **독자가 이미 아는 접두사·수식은 산문에서 생략한다.** 그 저장소 컨벤션이 정한 접두사(예: 공통 서비스의 `Common`)는 개발자가 아는 것이라 산문에선 줄인다. 클래스명·코드 블록·식별자는 원형 유지.

### 먼저 세우고 결론을 낸다

문서는 그 주제를 처음 보는 사람에게 **설명하는** 글이다. 결론만 박아놓으면 이해가 안 된다.

- **답을 이미 아는 사람만 아는 압축 라벨·은어를 쓰지 않는다.** 「get 인데 쓴다」·「왜 세트+1」처럼
  해독해야 뜻이 통하는 것은 안 된다. 항목 제목은 그것이 **무엇인지** 말하고, 설명은 기전을 사람 말로 푼다.
- **결정 절은 제목과 첫 문장에서 결론을 먼저 밝힌다.** 결론을 이해하는 데 필요한 용어만 먼저 정의한다.
  결론 뒤에 이유, 처리 방식, 경계 조건을 설명한다.
- **독자가 다른 문서의 짧은 문체를 그대로 옮기지 않는다.** 형식은 따르되 내용은 세워서 설명한다.
- **쉽게 쓰려다 틀리지 않는다.** 귀에 붙는 요약·라벨이 사실과 어긋나거나 다른 장과 모순되면 안 된다.
  코드가 정본이고, 압축해도 정본과 맞아야 한다. 압축한 문장은 코드·다른 장과 다시 대조한다.

### 문단·배치·제목

읽는 사람은 훑는다. 제목과 절의 첫 문장만 읽고 관심 있는 절만 내려간다. 글자 수 규칙은 두지 않는다.
길이는 참고값일 뿐이고, 읽히는가를 정하는 것은 문단을 어떻게 나누고 무엇을 어디에 두느냐다.
기준 실물은 토스페이먼츠 개발자센터의 「멱등성이 뭔가요?」(docs.tosspayments.com/blog/what-is-idempotency)다.
어휘·문장 구성이 사람이 쓴 글의 기준이다. 해요체만 평어체로 옮긴다.

- **결정을 말하는 절만 결론 문장 제목, 나머지는 명사구.** `##` 가 결정을 말하면 번호 + 결론(「차감은 원자적 조건부 UPDATE 한 문장이다」),
  설명·목록·색인 절이면 명사구(「문서 종류」). `###` 는 항상 짧은 명사구. 「문서는 세 종류다」처럼 설명 절을 억지로 문장으로 만들지 않는다.
  「개요」「배경」「결론」 같은 기능 이름 제목과 **제목 속 개수**(「근거 문서 두 편」)는 쓰지 않는다.
- **표 머리는 짧은 명사 한 단어**(「결정」「시나리오」). 「무엇을 왜 택했나」 같은 질문형·문장형 열 이름을 쓰지 않는다.
- **정보의 관계에 따라 형식을 고른다.** 비교·대응·조건별 차이는 표, 같은 위상의 원칙·조건·사례는 목록, 순서는 번호 목록이나 단계 흐름으로 표현한다.
- **표 셀에 문장이 둘 이상이면 문장마다 줄을 바꾼다.** 서로 다른 결정이면 행을 나눈다.
- **제목 바로 아래 첫 문장이 그 절의 주장이다.** 제목만 읽고 넘어가는 독자가 첫 문장에서 답을 얻는다.
- **독자가 따로 찾아볼 내용에는 소제목을 붙인다.** 결정 이유, 처리 흐름, 경계 조건, 확장 경로처럼 내용의 역할이 바뀌는 지점이 기준이다. 한 문단으로 끝나는 짧은 보충 설명에는 소제목을 만들지 않는다.
- **한 문단 한 요점.** 정의 문단, 예 문단, 대조 문단, 자기 결정 문단을 따로 둔다.
  일반 원리와 이 저장소의 결정은 문단을 가른다(「IETF 는 헤더를 표준으로 제안한다」 다음 문단에 「이 저장소도 헤더 방식이다」).
- **정의는 「정의 → 즉, 한 줄 요약 → 도메인 안의 예」.** 일상 비유(곱하기 1·절대값)는 쓰지 않는다.
- **표·코드·그림은 그것을 가리키는 문장 바로 다음에.** 「아래」로 가리킨다. 그림을 먼저 놓고 뒤에서 설명하지 않는다.
  표 밑에 출처 한 줄, 참고 자료 목록은 문서 끝에.
- **절 순서는 넓은 것에서 좁은 것으로.** 정의 → 왜 문제인가 → 기전 → 우리 결정 → 경계·거부 → 참고.
- **단계는 번호 목록, 한 단계 한 문장.** 분기는 3-1 / 3-2 로 가지를 달고, 보충은 그 단계 아래 들여쓴다.
- **원인과 결론이 이어지는 추론은 산문으로 쓴다.** 순서, 대응 관계, 같은 위상의 조건·원칙·사례는 목록이나 표로 구조를 드러낸다. 조각을 대시로 잇지 않고 「~기 때문에」「~라면」「반면」「또」로 한 문장 안에서 잇는다.
  이유 연결 「~기 때문에」는 열 문장에 한 번꼴을 넘기지 않는다.
- **가르치는 장치를 쓰지 않는다.** 독자가 상급자·채용 담당자·CTO 인 문서에서 질문형 제목, 「~살펴볼까요?」 같은 전환 질문,
  「알고 보면 쉽다」 같은 안심 문장은 뺀다. 「질문 → 답」은 「문제 문장 → 답」으로 바꾼다.
- **외래 기술 용어는 한글 표기 그대로**(리소스·타임아웃·헤더). 첫 등장에만 원어를 괄호로 한 번.
  은어는 「(일명 '따닥')」처럼 따옴표와 일명으로 한 번만.
- **행위자가 달라지거나 헷갈릴 수 있는 문장에는 주체를 쓴다.** 같은 문단에서 주체가 유지되고 오해할 여지가 없으면 반복을 생략한다. 피동은 상태를 말할 때만(저장되어 있던 응답) 쓰고, 행위자가 있으면 능동으로 쓴다.
- **동사는 도메인 명사 + 하다.** 구매·판매·선점·해제·차감·복원·승인·취소·재발급·측정·조회.
  사다·팔다·잡다·놓다·붙잡다·갚다·재다·묻다(시스템 사이) 같은 구어 동사를 쓰지 않는다. 「부하로 잰」이 아니라 「부하로 측정한」, 「토스에 물어」가 아니라 「토스 조회 API 로 확인해」.
  「지금 살 수 있는지」가 아니라 「구매 가능 여부」다. 독자는 상급자·채용 담당자·CTO 다.
- **「경합」은 락 경합처럼 자원을 두고 기다리는 상황에만.** 동시에 들어온 요청은 「동시 요청」「중복 요청」이다.
  이 분야 용어라도 처음 나오는 자리에서 한 번 세운다(「여러 요청이 같은 행을 동시에 수정하려다 서로 기다리는 것」).
- **페이지·절·요소는 사람이 부르는 말로.** 「색인」이 아니라 「문서 목록」, 「결론 상자」가 아니라 「요약」.
  CSS 클래스명·내부 용어·「핫패스」 같은 정의한 적 없는 말을 산문에 쓰지 않는다.
- **옛 문장을 새 자리에 옮길 때도 이 규칙을 적용한다.** "나중에 고친다"며 그대로 싣지 않는다. 옮기는 순간이 고치는 순간이다.

### 일반어 검사

리뷰에서 걸리는 말의 절반은 한 원인이다. 코드 상수나 영어 개념어를 한자어 한 단어로 직역한 것.
활성(ACTIVE) · 불투명(opaque) · 가용(available) · 순번(auto increment) · 핫패스(hot path) · 실측(measured) · 스윕(sweep) · 슬라이스(slice).
저장소 안에서 굳은 말이라 쓰는 사람은 일반어로 착각한다. 판단 기준은 「맞는 말인가」가 아니라 **「보통 사람이 그 뜻으로 쓰는 말인가」**다.

- **직역 한자어를 쓰지 않는다.** 사람이 부르는 말로 푼다(활성 → 판매 중, 불투명한 → 추측할 수 없는, 순번 → 순서대로 증가하는 숫자).
  그 분야 용어라 바꿀 수 없으면 첫 등장에 정의한다(가용 → 판매 가능 수량, 실물에서 예약을 뺀 값).
- **검사 기준은 둘이다.** 템플릿 문서에서 본 말인가. 이 분야 밖 사람이 같은 뜻으로 쓰는 말인가. 둘 다 아니면 바꾼다.
- **주어는 행위자, 서술어는 동사.** 사용자·서버·스케줄러·운영자가 무엇을 하는지 쓴다.
  대상을 주어에 세우고 동사를 빼서 「명사는 명사다」로 접지 않는다. 「핫딜은 여기서 예약한다」「추가 물량은 새 회차다」가 그 꼴이다.
  핫딜은 예약하지 않는다. 핫딜을 등록하면 서버가 재고를 예약한다.
- **초안을 쓴 뒤, `humanize-korean` 진단 전에 어휘 대조를 한다.** 도메인 명사·동사·한자어를 하나씩 위 기준으로 본다.
  진단은 쉼표와 리듬은 잡아도 이 단어들은 못 잡는다. 대조한 단어와 바꾼 것을 체크포인트 보고에 적는다.
- **리뷰에서 지적받은 표현은 먼저 해당 문서에서 고친다.** 여러 문서 형식과 다른 저장소에서도 반복될 원인을 찾았고 기존 규칙으로 설명할 수 없을 때만 전역 규칙으로 올린다.
  특정 도메인·형식에만 해당하면 저장소 규칙에 둔다. 걸린 단어 하나가 아니라 그 단어가 걸린 **원인**을 규칙으로 적는다.
- `humanize-korean` 은 재작성기가 아니라 검사기다. **문서 하나를 끝내면 커밋 체크포인트 전에** 산문만 뽑아 진단(diagnostician)을 받고
  지적된 곳만 손본다. 재작성본을 되붙이지 않는다. 진단 결과(패턴·건수·고친 곳)를 체크포인트 보고에 적는다. 안 돌렸으면 안 돌렸다고 적는다.

### 코드를 실을 때

- **코드 흐름은 화살표 나열이 아니라 실제 코드에 가까운 의사코드로 적는다.** `payload ─fn→ DTO` 식 화살표는 실제 코드와 동떨어져 읽기 어렵다. 실제 메서드를 기준으로 타입·구조를 살리고, 타입을 변수 선언에 얹어 데이터 흐름을 코드 안에서 드러낸다. 짧은 메서드도 생략하지 않는다.
- **코드 블록은 전 곳 같은 방식으로 맞춘다.** 한 곳만 다르면 눈이 걸린다. 어느 클래스·흐름인지 헤더를 달고, 주석에 목적을 함께 적는다. 한 곳을 고치면 나머지가 같은지 전수 확인한다.
- **도메인·타입 이름은 코드 식별자로 통일한다.** 한글로 섞지 않고(「파일 도메인」 ✗ → `File 도메인` ✓), 은어를 만들지 않는다.
- 긴 줄·주석은 잘리므로 폰트를 줄이거나 줄을 나눠 좌우 넘침 0 을 렌더로 확인한다. (색·폰트 등 구체값은 저장소 규칙)

### 문체만 고칠 때 사실을 건드리지 않는다

- 코드 식별자·수치·경로·인용·각주·상호참조는 **원문 그대로** 둔다.
- 고친 뒤 원문과 **기계로 대조**해 이것들이 안 바뀌었는지 확인한다.

### HTML 로 쓸 때

- **HTML 요소와 CSS 로 정보의 관계를 드러낸다.** 핵심 결정은 요약, 비교는 표, 순서는 단계 흐름, 반복되는 결정은 카드, 긴 코드와 보충 근거는 `<details>` 를 쓸 수 있다. 마크다운 구조에 태그만 바꿔 붙이지 않는다.
- **핵심 결정과 선택 이유는 펼쳐 둔다.** 코드, 긴 근거, 드문 경계 조건만 접는다.
- **CSS 는 장식보다 정보의 위계와 묶음에 쓴다.** 색·그림자·애니메이션을 늘리기 전에 제목, 간격, 정렬, 그룹으로 관계를 보여준다.
- **같은 구조가 반복돼 읽는 흐름을 끊으면 더 단순한 형식으로 바꾼다.** 카드가 많으면 목록이나 표를 검토한다.
- **모바일에서도 정보 순서를 유지한다.** 여러 열은 한 열로 바꾸고, 표의 가로 스크롤은 페이지 전체가 아니라 표 영역 안에서만 생기게 한다.

### 슬라이드로 쓸 때

템플릿·토큰명·수치는 그 저장소 규칙에 있다. 여기엔 어느 저장소에서나 같은 것만 둔다.

- **소제목은 굵기가 아니라 색으로 구분한다.** 본문에도 굵게를 쓰므로 굵기만으로는 구분이 안 된다.
  `text-transform:uppercase` 는 한글에 효과가 없고 `font-family:mono` 는 한글을 폴백으로
  떨어뜨려 자간만 벌어진다 — 코드 식별자만 따로 감싼다.
- **강조 장치는 위치가 아니라 뜻으로 쓴다.** 배경 반전·강조색은 그 장에서 가장 중요한 항목에만.
  "마지막이니까" 는 이유가 아니다.
- **항목이 짧고 서넛이면 카드가 아니라 가로 번호 행이다.** 카드는 문단이 여럿일 때 쓴다.
- **여백을 억지로 채우지 않는다.** `space-evenly` 로 요소를 벌려 빈칸을 감추는 것은 가독성이 아니다.
  남는 공간은 그대로 두거나 구조를 바꾼다.
- **클릭 넘김이 드래그를 막지 않게 한다.** 좌우 클릭으로 장을 넘기는 스크립트는 `mousedown` 좌표를
  기억해 6px 넘게 움직였거나 `window.getSelection()` 이 비어 있지 않으면 넘기지 않는다.
  이게 없으면 코드 블록을 드래그해 복사하려 할 때마다 장이 넘어간다.
- **코드 블록에 색을 넣으면 IDE 색을 따른다.** IntelliJ 활성 스킴은
  `~/Library/Application Support/JetBrains/IntelliJIdea*/options/colors.scheme.xml` 이 가리키고,
  `.icls` 는 부분 저장이라 플러그인 원본(`plugins/*/lib/*.jar` 안 `themes/*.xml`)과 **합쳐야**
  실제 색이 나온다. 폰트·행간은 문서 값을 유지한다 — 슬라이드 타이포그래피가 따로 잡혀 있다.
- **윤문은 작성 후 별도로 한다.** HTML 태그가 섞인 채로 돌리면 마크업이 깨진다.
  문장 블록만 뽑아 `humanize-korean` 을 돌리고 결과를 되반영한다.

### 실제 산출 형태로 확인한다

「작업 성향」의 「검증」을 문서에 적용한 것이다.

- 산출물은 사용자가 볼 **실제 형태·크기로 렌더**해 확인한다. 축소 미리보기로 통과를 판단하지 않는다 — 작은 창에서 멀쩡하던 것이 실제 화면에서 잘린다.
- 정해진 틀이면 내용이 잘리거나 **바닥에 딱 붙지 않는지** 전 장을 본다. 안 들어가면 글자를 줄이기 전에 쪼갠다. 가독성이 떨어지면 분량을 늘려도 되지만 남발하지 않는다.
- **하단 여백은 남기는 게 아니라 나눈다.** 「바닥에 딱 붙지 않게」가 바닥을 비워도 된다는 뜻은 아니다. 성긴 장은 내용을 키우거나 세로로 가운데 정렬해 여백을 위아래로 나눈다.
- **표 셀에 줄바꿈 금지(`nowrap`)를 남발하지 않는다.** 설명 칸이 `nowrap` 이면 열 폭을 넘겨 옆 칸과 겹친다. 짧은 칸만 `nowrap`, 설명 칸은 wrap.
- **좌우 2단 레이아웃은 「컬럼 밖으로 삐져나오는지」로 겹침을 잰다.** 자주 놓치는 실수다 — 표·코드 블록의 **자체 스크롤폭(`el.scrollWidth`)만 보면 못 잡는다.** `nowrap` 셀이 표를 제 칸보다 넓혀도 표 요소 자체는 넘침으로 안 잡히고, 넘친 부분이 옆 칸으로 삐져나와 글자가 겹친다. **컬럼(칸) 박스**의 `scrollWidth > clientWidth`(칸 밖으로 넘친 content)나 왼쪽 칸의 오른쪽 끝이 오른쪽 칸 왼쪽 끝을 넘는지(`getBoundingClientRect`)로 잰다. 겹치면 그 칸을 넓히거나(`1fr 1fr` → `1.32fr 1fr`) `nowrap` 을 풀거나 글자를 줄인다. (렌더 없는 CI 로는 못 봐서 이 검사는 렌더로만 한다)
- 이미 정해진 템플릿·형식은 **요구가 있을 때, 요구된 부분만** 바꾼다.
- 확인한 것을 항목별로 보고한다.

### 대량 편집은 백업하고 자체 검증한다

- 번호 재매김·일괄 치환 같은 기계 편집은 **먼저 백업**하고, 결과를 스크립트로 검증한 뒤 신뢰한다 — 정규식 하나가 조용히 옆엣것을 오손한다.
- 구조를 바꾸면 번호·상호참조·목차가 어긋나지 않았는지 전수 확인한다.

### 결정 이력과 검증 사례

「대화의 흔적을 문서에 옮기지 않는다」는 그대로다. 논쟁을 재현한 방어 문단은 그 논쟁을 모르는 독자에게 뜬금없다. 다만 **결과**는 정해진 자리에 정해진 꼴로 남긴다.

- **결정이 뒤집힌 문서는 끝에 「바뀐 결정」 표를 둔다.** 열은 날짜 · 이전 · 이후 · PR 댓글 링크. 한 줄이 한 번의 번복이다. 과정은 적지 않는다 — 타임라인은 PR 에 있다.
- **검증 사례는 PR 댓글과 커밋의 `검토:` 줄에서만 가져온다.** 기록에 없는 주체(「사람이 잡았다」·「AI 가 제안했다」)는 적지 않는다. 기록 이전의 사례는 「누가 무엇을 했나」를 사용자에게 한 번 묻고 답을 그대로 받아 적는다. AI 가 지어 쓰면 포장이 되고 면접에서 드러난다.

### AI 협업 문서

포트폴리오 저장소에는 AI 와 어떻게 일했는지를 설명하는 문서 한 편을 둔다. 규칙을 복제하는 문서가 아니라 검토자가 검증 흔적을 따라갈 수 있게 하는 문서다. README 에는 이 문서로 가는 한 줄만 둔다.

절 순서는 ADR 골격을 따른다.

1. 요약 3줄 — 역할 분담 / 검증이 몇 겹인지 / 흔적이 어디 있는지
2. 문서를 먼저 쓰게 하는 이유 — AI 가 어떤 의도로 만들려는지 문서로 먼저 읽고, 이해하지 못한 것은 구현으로 넘어가지 않는다는 것
3. 역할·검증·흔적 표 — 단계마다 「AI 가 하는 것 / 사람이 하는 것 / 근거가 되는 설정 / 흔적이 남는 곳」
4. 검증 사례 하나 — 위 「검증 사례」 규칙대로 기록에서만
5. 경계 — 산문은 AI 가 쓴다는 것, 대화 기록은 공개하지 않는다는 것, 전역 규칙은 저장소 밖에 있다는 것을 담백하게
6. 규칙 파일 위치 — 링크만

AI 활용을 자랑하는 문서가 되면 안 된다. 보여줄 것은 규칙의 양이 아니라 검증이 돌았다는 증거다.

## ponytail

`ponytail` 플러그인이 `SessionStart`·`SubagentStart` 훅으로 **모든 세션·모든 저장소에 자동
주입된다.** 스킬을 부르지 않아도 켜져 있고 기본 강도는 `full` 이다. 끄려면 메시지 전체를
`stop ponytail` 로 보낸다.

강도는 `full` 로 둔다. `ultra` 는 요구사항 자체를 먼저 따지는데, 그건 「범위」의 「요청받은 것을
요청받은 범위로 낸다」와 부딪힌다.

사다리 자체는 「범위」와 같은 말이라 충돌이 없다 — 요청에 없는 추상화·방어 코드를 안 붙이고,
표준 라이브러리와 이미 깔린 의존성을 먼저 본다.

**이 문서가 이긴다.** ponytail 이 요구해도 아래는 따르지 않는다.

| ponytail 이 요구하는 것 | 이 문서 |
|---|---|
| 코드 먼저, 설명은 최대 세 줄 | 커밋 체크포인트의 작업 내역과 추천 커밋 명령, 슬라이스 완료 시 인수 확인 항목별 리스트업, 디버거로 본 값, 슬라이스 진행 표는 전문으로 낸다. ponytail 자신의 「요청받은 설명은 부채가 아니다」에 해당한다 |
| 테스트 프레임워크·fixture 금지, `assert` 자체검사 하나 | 「TDD」 절이 이긴다. 사이클마다 커밋하고 그 저장소가 쓰는 테스트 도구를 쓴다. ponytail 의 테스트 절은 Python 전제다 |
| 구현이 하나뿐인 계층·추상화는 `yagni` | **그 저장소의 CLAUDE.md 가 확정한 계층·폴더·이름 규칙은 `yagni` 대상이 아니다.** 지금 호출자가 하나여도 마찬가지다. 규칙을 지운 diff 가 짧아 보이는 것은 근거가 안 된다 |
| 미룬 것은 `ponytail:` 주석으로 | 그 저장소가 이미 쓰는 마커를 쓴다. 마커를 둘로 늘리지 않는다 |

마지막 줄 때문에 **`/ponytail-debt` 는 대개 빈손이다.** 그 스킬은 `(#|//) ?ponytail:` 만
grep 하므로 저장소 고유 마커를 못 잡는다.

### review 는 쓰고 audit 은 안 쓴다

`/ponytail-review` 는 **diff 한정**이라 쓴다. 부를 때 아래를 같이 읽는다.

**지적하지 않는다** — 그 저장소의 CLAUDE.md 가 확정한 것이라 「구현이 하나뿐」이 근거가 안 된다.

- 계층·폴더·이름 규칙이 만든 파일과 클래스 — 지금 호출자가 하나뿐인 것을 포함해서
- 규칙 하나에 테스트 하나씩 두는 구조
- 그 문서가 예외로 허용한 주석

**지적한다** — 태그는 ponytail 것을 그대로 쓴다.

- `stdlib:` 표준 라이브러리나 프레임워크가 이미 하는 것을 손으로 짠 것
- `native:` 이미 깔린 의존성이 하는 것을 새로 짠 것
- `delete:` 안 불리는 코드, 아무도 안 세팅하는 설정, 이미 닫힌 TODO
- `shrink:` 같은 로직을 더 짧게
- `yagni:` **위 「지적하지 않는다」에 없는** 추상화만

**그 저장소의 경계 규칙은 `boundary:` 를 더해 본다.** CLAUDE.md 에 계층 경계가 적혀 있으면
그 위반이 ponytail 다섯 태그 어디에도 안 들어간다.

`net: -N lines` 는 그대로 내되 **계층 규칙이 만든 파일 수는 그 숫자에 넣지 않는다.**

`/ponytail-audit` 는 쓰지 않는다. 저장소 전수로 돌면 위 표 셋째 줄에 해당하는 것을 전부 삭제
후보로 올려, CLAUDE.md 가 확정한 결정을 되돌리는 목록이 나온다. 넓게 보고 싶으면 review 를
큰 diff 에 건다.
