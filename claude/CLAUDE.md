# 전역 작업 규칙

- 한국어로 대화하고 한국어로 산출한다. 코드 식별자와 외부 인용만 원문 유지.
- 사고 과정(thinking)도 한국어로 작성한다. 코드 식별자와 외부 인용만 원문 유지.
- 파일을 수정하기 전에 그 파일을 먼저 읽는다.
- **커밋·푸시는 사용자가 직접 한다.** 자동으로 커밋하지 않는다.

## 작업 성향

- **간결성**: 응답과 산출 문서를 필요한 만큼만 작성한다. 결론을 먼저, 근거는 그 다음. 요약을 중복하거나 형식을 채우려고 섹션을 만들지 않는다.
- **범위**: 요청받은 것을 요청받은 범위로 낸다. 사소한 판단은 스스로 결정하고 한 줄로 알린다. 요청에 없는 리팩터링·추상화·방어 코드를 추가하지 않는다. 더 나은 접근이 보이면 한 줄로 제안하고, 요청받은 대로 진행한다.
- **서브에이전트**: 직접 몇 번의 도구 호출로 완료할 일은 위임하지 않는다. 방금 수행한 작업의 결과를 재확인하려고 위임하지 않는다. 위임은 독립적이고 규모 있는 작업(다중 파일 광범위 조사)에만 한다.
- **모델**: 서브에이전트 정의에 `model:` 을 명시하지 않는다. 세션 모델을 상속시킨다 — 프롬프트 캐시는 모델 단위라 다른 모델을 지정하면 매번 캐시를 활용하지 못하고, 모델 선택은 사용자 설정의 권한이다. 하네스 메타스킬이 `model: "opus"` 를 강제하더라도 따르지 않는다.
- **검증**: 테스트·빌드를 실행하지 않고 통과를 주장하지 않는다. 실행하지 못했으면 그 사실을 밝힌다. 슬라이스 완료 시점의 인수 확인은 「TDD」 섹션에 있다.
- **교차 검증**: 사용자가 요구하거나, 사용자의 리뷰에 답하거나, 공개 문서·중요한 설계 판단의 최종안을 제시할 때는 `codex-cross-check` 스킬로 Codex 와 교차 검증한다. Codex 를 사용할 수 없으면 생략하고 그 사실과 검증하지 못한 범위를 알린다.
  **Codex 호출에 `--json`·`| tail` 을 추가하거나 출력을 파일로 리디렉션하지 않는다.** 하나만 있어도 사용자 화면에 진행 상황이 표시되지 않는다. `tail` 은 스트림이 끝나야 출력하고 `--json` 은 완료 시점에 한 덩어리로 출력하며 `> 파일` 은 화면에 아무것도 남기지 않는다. 오래 걸리면 Bash 백그라운드로 그대로 실행한다. 그러면 `[codex]` 진행 줄이 백그라운드 작업 패널에 실시간으로 표시된다. 긴 프롬프트는 파일에 작성해 두고 `--prompt-file 절대경로` 로 전달한다. 상대 경로는 `--cwd` 기준으로 해석된다.
- **브라우저**: 화면 확인·조작이 필요하면 `ego-browser` 스킬을 기본으로 사용한다. 한 번 호출에 이동·대기·스크린샷을 스크립트로 묶을 수 있고 파일을 임시 작업 폴더에 바로 저장하며, 종료할 때 `finish({ keep })` 로 그 탭을 사용자 화면에 남겨 전달할 수 있다. 로그인이 필요하면 `handOff()` 로 전달하고 사용자가 로그인한 뒤 같은 작업 공간을 이어받는다.
  **한 대화의 검수는 한 작업이다.** 중간 확인마다 `finish` 를 호출하지 않고 같은 공간과 탭을 재사용한다. 사용자에게 전달한 공간은 다시 닫기 어렵다(마지막 탭이 남는다). 결과 화면을 보여 줄 때만 `finish({ keep })` 로 전달한다. 보고에는 spaceId 와 열어 둔 화면을 기록한다. 전달한 공간이 다시 필요하면 `claimTaskSpace` 로 가져온 뒤 `tabs()` 로 열린 화면을 확인한다. 사용자가 사용하는 화면이 없을 때만 `adopt` 해서 이어서 사용한다. 있으면 조작하지 말고 `finish({ keep })` 로 곧바로 반환한 뒤 어떻게 할지 질문한다. 자기가 전달한 공간을 이렇게 되찾는 것은 이 규칙으로 승인된 것으로 간주한다.
  예외는 둘이다. 지금 켜져 있는 사용자의 Chrome 창·확장·SSO 세션이 필요하면 `claude-in-chrome`, 네트워크 가로채기나 트레이스처럼 Playwright 고유 기능이 필요하면 Playwright 를 사용하고 그 이유를 한 줄로 알린다.
- **보여주기와 명령**: 사용자가 확인해야 할 내용은 답변에 직접 포함한다. `cat` 같은 조회 명령을 사용자에게 요청하지 않는다. 실행할 명령은 실제로 실행해야 하는 것만, 그 직전에 상태(`git status`·PR 상태 등)를 확인한 뒤 제시한다.
- **대화도 문서처럼**: 사용자에게 제시하는 답변과 질문도 「문서 작성」 규칙을 따른다. 짧은 문장, 일상 말, 지시어 대신 대상 이름. 일상 말은 대화의 기준이다. 문서의 문체는 doc-writing 이 결정한다. 초안은 표 칸 안에 숨기지 않고 표 밖에 별도로 제시한다. 선택지마다 설명이나 초안이 길면 질문 창 대신 채팅에 질문과 선택지를 작성한다.
- **리뷰 답변**: 사용자가 여러 항목의 리뷰를 전달하면서 수정하라고 하지 않았으면 항목마다 수용 여부와 변경 내용을 먼저 답하고 확인을 받은 뒤 수정한다.
- **정직성**: 추측을 사실처럼 말하지 않는다. 근거가 되는 파일·명령 출력이 있으면 그것을 제시하고, 없으면 없다고 밝힌다.
- **기록 위치**: 어디에 기록할지는 「전역 규칙 → 저장소 규칙(CLAUDE.md·문서) → 메모리」 순서로 선택한다. 다른 저장소에서도 같은 판단을 할 것이면 전역 규칙, 그 저장소의 사실·결정이면 저장소 문서, **이번 작업에서만 사용하고 끝날 것만 메모리**에 둔다. 메모리는 보수적으로 사용한다 — 작업 방식이 메모리에 쌓이면 다른 저장소로 옮겨지지 않는다.
- **기술 도입 조건**: 포트폴리오 저장소에 기술을 도입할 때는 네 가지가 갖춰져야 한다. 문제 문장(이 서비스에서 무엇이 안 되는가. 트래픽 관측이 아니라 서비스 목표에서 도출해도 된다), 가설, 재현과 측정(도입 전 수치를 먼저 기록하고 도입 후를 같은 격자로), 한계와 되돌림 조건. 하나라도 없으면 그 기술은 문제와 연결되지 않은 것이다.

## 모호하면 먼저 질문 (탐색은 그 다음)

**사용자가 아는 사실**(진행 상황·완료 여부·범위·의도)이 모호하면, 도구로 탐색하지 말고 먼저 질문한다. "모른다"는 답을 받은 뒤에 탐색한다.

- ❌ "지난주 계획 2건을 주간보고에 녹여줘" → 곧장 git log·레포 전수 조사로 진행 상황 추정
- ✅ "그 2건 이번 주 진행 상태가 어떻게 되나요? (완료 / 진행 중 / 미착수, 어느 요일)" 먼저 질문

사용자가 아는 것을 추측·조사로 보완하지 않는다. 질문이 더 빠르고 정확하다.

### 스킬 호출은 탐색이 아니다

스킬을 검색하고 호출하는 것은 위 규칙의 "탐색"에 해당하지 않는다. 즉시 실행해도 된다. 금지되는 것은 **사용자가 아는 사실을 도구 조사로 추정하는 것**이다.

세션 시작 시 주입되는 superpowers 의 `<EXTREMELY_IMPORTANT>` 지침("스킬 확인이 질문보다 먼저")과 이 규칙이 충돌하는 것처럼 보이면, **이 문서가 우선한다.** 스킬은 먼저 확인해도 되고, 사용자가 아는 사실은 여전히 먼저 질문한다.

문서를 작성하거나 수정하기 전의 캐묻기는 doc-writing 「쓰기 전에 캐묻는다」가 선택한 `grill-me`·`grill-with-docs` 로 진행한다. 계획·설계 문서는 문서가 속한 프로젝트의 규칙이 정한 형식으로 작성한다. `superpowers:brainstorming` 이 명세 파일을 생성하고 `superpowers:writing-plans` 로 전달하라고 요구해도 이 순서와 형식을 변경하지 않는다.

## 커밋 체크포인트

작업 단위마다 멈춰 작업 내역과 **추천 커밋 명령**을 제시하고 사용자 커밋을 기다린다.

**추천 커밋 명령은 항상 `cd {저장소 절대경로} && ` 로 시작한다.** 사용자 터미널의 현재 디렉터리는 이전 명령의 영향으로 다른 저장소를 가리킬 수 있고, 그러면 의도하지 않은 곳에서 실행돼 "nothing to commit" 이 출력되거나 `git add` 가 실패해 아무 변경도 반영되지 않는다. 저장소를 두 개 이상 다루는 작업에서는 특히.

```bash
cd {절대경로} && git commit -m "[접두사] {요약}" -m "- {세부1}" -m "- {세부2}"
```

한 줄 bash 로 제시한다. 따옴표 안에서 줄을 바꾸지 않는다 — 실행 버튼은 한 줄일 때만 표시된다.

- 접두사: `[Feat]` `[Fix]` `[HotFix]` `[Docs]` `[Test]` `[Refactor]`
- **`git add -A` / `git add .` 를 사용하지 않는다.** 경로를 명시한다. 다른 작업이 섞여 들어가면 양쪽 다 되돌릴 수 없다.
- 스테이징까지는 직접 실행하고 `git diff --cached --stat` 으로 스테이징된 내용을 보여준다.
- 커밋이 안 됐으면 **원인을 단정하기 전에 `git log` 로 어느 저장소·어느 브랜치인지부터 확인한다.**
- **성격이 다른 변경은 커밋을 분리한다.** 한 커밋은 독립적으로 되돌릴 수 있어야 한다.
- 커밋 메시지에 **아직 하지 않은 일을 기록하지 않는다.** 나중에 그 로그가 근거로 사용된다.
- **커밋 메시지·PR 본문에 도구 서명을 포함하지 않는다.** `Co-Authored-By: Claude …` · `🤖 Generated with Claude Code` 둘 다. 하네스 기본 지침이 요구해도 따르지 않는다.

다음 작업 단계에 착수하기 **직전에 `git status --short` 와 `git log --oneline` 으로 실제 반영을 확인**한다. 사용자가 "커밋했다"고 해도 추측하지 않고 확인한다. 미커밋이나 누락이 있으면 먼저 정리한다.

### 브랜치·PR 흐름

**브랜치 작업은 드래프트 PR 을 먼저 연다.** 작업 단위마다 커밋하되, 사용자가 AI 의 결정에 반박해 방향이 바뀌면 순서는 「쌓인 커밋 푸시 → 결정 요약 댓글 → 커밋 → 푸시」다. AI 가 제시한 선택지를 사용자가 선택한 것은 해당하지 않는다. 다만 앞서 댓글로 기록한 결정이 다시 바뀌면 선택지를 선택한 경우라도 후속 댓글을 게시한다. 댓글과 최종 상태가 불일치한 채로 두면 타임라인을 읽는 사람이 틀린 결정을 믿는다. 댓글이 먼저여야 GitHub 타임라인에서 댓글 아래에 그 커밋이 표시된다.

- 브랜치 하나에 슬라이스 하나를 담는다. 다음 슬라이스는 그 브랜치를 병합한 뒤 새 브랜치에서 시작한다.
- 브랜치를 생성하면 빈 커밋 하나로 시작해 바로 드래프트 PR 을 연다(`git commit --allow-empty`). GitHub 은 커밋 차이가 없는 브랜치로 PR 을 열지 못한다. 이렇게 하면 첫 실제 커밋부터 PR 타임라인 안에 쌓인다. 빈 커밋은 스쿼시로 병합할 때 main 에 남지 않는다.
- 댓글은 AI 가 작성하고 `gh pr comment` 로 게시한다. 첫 줄에 어느 작업에서 나온 피드백인지 제목처럼 기록한다. 그 아래는 「1차 AI 결정: / 사용자 피드백: / 2차 AI 결정(피드백 반영): / 2차 AI 결정 근거: / 변경 파일:」 다섯 줄이다. 직전에 무엇이 있었는지와 왜 그렇게 결정했는지가 없으면 지적이 왜 나왔는지 읽히지 않는다. 사용자 피드백은 받은 말을 그대로 옮기지 않고 요지를 공적인 문체로 기록한다. 공개 저장소의 기록이라 대화 맥락을 모르는 독자가 읽는다.
- 앞서 댓글로 기록한 결정이 다시 바뀌면 후속 댓글을 게시한다. 첫 줄에 어느 결정이 바뀌었는지 제목처럼 기록한다. 그 아래는 「직전 결정: / 다시 바뀐 계기: / 새 결정: / 새 결정 근거: / 변경 파일:」 다섯 줄이다.
- **댓글은 요약해서 짧게 작성한다.** 다섯 줄은 줄마다 한 문장으로 작성하고, 변경 파일 줄에는 파일 이름만 기록한다. 피드백이 여러 건이면 한 댓글에 모으지 않고 건마다 댓글을 별도로 게시한다. 댓글 하나가 길면 타임라인에서 그 결정이 읽히지 않는다. `git-guard` 가 댓글을 게시하기 전에 검사한다.
- Codex 교차 검증의 결과는 PR 댓글로 게시하지 않는다. 결과는 답변에서만 보고한다(`codex-cross-check` 「보고」). `git-guard` 가 「교차 검증 지적:」 줄이 있는 댓글을 차단한다.
- 그 커밋의 본문 첫 줄은 `검토: {지적} → {바뀐 것}` 이고 댓글 주소를 추가한다. 사용자 피드백 없이 진행한 커밋에는 추가하지 않는다.
- **댓글을 게시한 커밋은 추천 커밋 명령과 함께 푸시 명령도 제시한다.** 푸시까지 해야 PR 타임라인에서 댓글 아래에 그 커밋이 표시된다. 커밋 명령 바로 다음 블록에 `cd {저장소 절대경로} && git push` 를 별도로 제시한다. 브랜치에 업스트림이 없으면 `git push -u origin {브랜치}` 로 제시한다.
- 댓글을 게시하기 전에 푸시하지 않은 커밋이 있는지 확인한다. 있으면 푸시 명령을 먼저 제시하고 사용자가 푸시한 뒤 댓글을 게시한다. 쌓인 커밋을 댓글 뒤에 함께 푸시하면 그 커밋이 모두 댓글 아래에 표시되어 어느 커밋이 결정을 반영했는지 구분할 수 없다. `git-guard` 가 푸시하지 않은 커밋이 있으면 댓글을 차단한다.
- 댓글이 없는 커밋은 모아 두었다가 다음 PR 댓글을 게시하기 전이나 병합하기 전에 푸시한다.
- **PR 브랜치에서 `rebase`·`push --force` 를 사용하지 않는다.** 댓글과 커밋의 연결이 해시에 묶여 있어 이력을 재작성하면 끊긴다. 전역 settings 가 차단한다.
- **PR 은 스쿼시로 병합한다.** 스쿼시 본문은 PR 본문(작업 내용 / 검토에서 바뀐 것 / 인수 확인 결과 항목별)이다. PR 본문은 브랜치가 무엇을 변경했는지를 기록하는 자리다. 「지적 / 결정 / 바꾸는 것」 세 줄은 댓글의 형식이다. **PR 본문과 댓글도 「문서 작성」 규칙을 따른다.** 사람이 작성한 글로 읽혀야 한다. GitHub 기본값(브랜치 커밋 메시지 이어 붙이기)을 사용하지 않는다. TDD 사이클 이력과 댓글 타임라인은 main 이 아니라 PR 에 남는다. 문서에 「main 에 남는다」고 기록하지 않는다.

## TDD

테스트와 구현을 한 슬라이스씩 함께 작성한다. "전체 구현 후 테스트 몰아쓰기"는 하지 않는다.

한 사이클 = RED(실패 테스트 하나) → GREEN(그 테스트를 통과시키는 최소 구현). **각 단계를 별도 커밋**으로 한다.
GREEN 이 되면 멈추고 체크포인트 보고를 제시해 리뷰를 받는다. REFACTOR 는 리뷰에서 구조·중복 지적이 나왔을 때만 진행하고 완료하면 다시 리뷰를 받는다.
문서 갱신은 사이클마다 하지 않는다. 브랜치의 마지막 사이클을 커밋한 뒤 한 번 모아서 진행하고 `[Docs]` 커밋으로 제시한다. 문서 확인 절차(독자 테스트 등)를 사이클마다 실행하지 않기 위해서다.

- 메서드·enum 상수의 존재는 테스트로 정당화된다. 미리 작성해 두지 않는다.
- 다음 사이클을 미리 계획표에 기록하지 않는다. 한 사이클이 끝난 뒤 그 자리에서 다음 행위를 결정한다.
- GREEN 이 안 되면 우회하지 않는다. mock 과잉, 강제 flush, 운영과 다른 경로로 통과시키기 금지. 원인을 진단한다.

여러 슬라이스에 걸친 작업은 체크포인트마다 **지금 어디인지**를 표로 제시한다(슬라이스 목록 + 현재 사이클). 슬라이스 목록은 설계에 이미 있으니 미리 작성해도 되지만, **사이클 행은 완료한 것만 기록한다.**

### 슬라이스 완료 검증 — 앱을 띄워 밖에서 호출한다

슬라이스의 문서 갱신까지 마치고 마지막 커밋 체크포인트를 제시하기 전에, **이미 작성된 테스트를 다시
실행하는 것으로 끝내지 않는다.** 방금 GREEN 을 만든 그 테스트라 새로 알려 주는 정보가 없다.
검증은 **앱을 실제로 기동해 운영과 같은 경로로 호출해보는 것**이다.

1. 앱을 기동한다. JVM 프로젝트에서 IntelliJ IDEA 가 열려 있으면 `ij-debugger` 스킬로 디버그 실행해서, 사용자가 보고 있는 IDEA 화면에 AI 의 작업이 표시되게 한다.
   **DB·외부 의존은 일회용 컨테이너로 기동하고 개발용 인스턴스를 사용하지 않는다**
2. 이번 슬라이스가 구현한 흐름을 실제 프로토콜로 호출한다 — 테스트 하네스가 아니라 HTTP·CLI 로
3. 정상 경로만 확인하지 않는다. 경계·거부·오류 응답이 나오는 요청까지 한 번씩 호출한다
4. 완료하면 프로세스와 컨테이너를 정지한다

**수행한 인수 확인을 답변에 항목별로 리스트업한다.** 무엇을 어느 주소로 어떻게 호출했고
응답 코드와 본문이 무엇이었는지를 항목마다 기록한다. "정상 동작 확인" 한 줄로 합치지 않는다.
기동하지 못했으면 그 사실과 이유를 기록한다 — 실행한 척하지 않는다.

디버거로 기동했으면 호출과 함께 디버거로도 확인한다. 응답만으로 왜 그 값이 나왔는지 구분되지 않는 곳,
그리고 코드를 작성하지 않고 중단점에서 멈춰 다른 요청·명령을 전송해 볼 수 있는 경우가 대상이다.

- 확인 대상은 **테스트가 단언하지 않는 것**이다 — 실제로 흐른 값, 어느 분기로 실행됐는지, 호출 순서, 그 줄이 실행되기는 하는지
- 정지 없는 로그포인트(logpoint)로 먼저 증거를 수집하고, 부족하면 중단점·스텝·표현식 평가로 단계를 높인다
- **확인한 것을 체크포인트 보고에 기록한다.** 어디에 무엇을 설정해 어떤 값을 확인했는지
- 개별 RED/GREEN 사이클마다 적용하지 않는다. 루프가 느려지고 스킬도 발동 조건에서 제외된다

전제는 IDEA MCP 서버(`설정 | 도구 | MCP Server`)가 켜져 있고 `xdebug_*` 도구가 세션에 로드된 것이다.
도구가 없으면 **없다는 사실을 먼저 알리고** 인수 확인 결과만으로 보고한다. 연결한 척하지 않는다.

## 막혔을 때

같은 실패가 반복되면 추측으로 수정하지 않는다. **무엇을 시도했고, 무엇이 실패했으며, 어떤 판단이 필요한지**를 보고하고 멈춘다.

## 세션 분할 제안

새 세션으로 전환하는 편이 나은 신호가 보이면 강제하지 말고 먼저 제안한다.

- 작업 단위(도메인·슬라이스·주차)가 완결되고 다음이 별개 단위일 때
- 컨텍스트가 길어져 성능 저하가 우려될 때
- 다음 작업이 현재 대화 맥락에 거의 의존하지 않고 문서·코드·git 으로 복원 가능할 때

제안 시 **이유**와 **인계 프롬프트**(현재 상태·다음 작업·참고 문서)를 함께 제시한다. 유지할지 분할할지는 사용자가 결정한다.

## 표현

코드 식별자(클래스·메서드·패키지·어노테이션명)는 영어 그대로. **그 외 개념은 한국어로 풀어 쓴다.**

| 사용하지 않는 표현 | 풀어 쓰기 |
|---|---|
| 영합 | 그냥 동의 / 비판 없이 따라가기 |
| anticipation | 미리 앞질러 짐작하기 / 미리 분배하기 |
| Tracer Bullet | 한 번에 끝까지 통과시키는 첫 시도 / 기존 동작 명세화 |
| horizontal slicing | 테스트만 모아 쓰고 구현만 모아 쓰는 잘못된 방식 |
| vertical slicing | 테스트 하나 → 구현 하나씩 번갈아 쌓는 방식 |
| PROPAGATION_REQUIRED | 기존 트랜잭션 있으면 합류 (Spring transaction propagation 모드) |
| PC (PersistenceContext) | JPA 가 객체 추적하는 메모리 공간 |
| FlushMode.AUTO/MANUAL | hibernate 자동 flush 시점 정책 |
| invariant | 호출 계약상 항상 성립하는 조건 |

- 처음 등장 시 한국어로 풀고 괄호로 원문 병기 가능 — "기존 트랜잭션 합류(PROPAGATION_REQUIRED)"
- 두 번째부터는 코드 식별자만 영어, 개념은 풀어 쓰기
- 한자어라도 일상에서 사용하지 않는 단어("영합")는 풀어 쓰기

**"회귀(regression)"를 넓게 사용하지 않는다.** 이미 통과하던 것이 깨진 경우에만 사용한다. 그 외에는 실제로 뜻하는 바로 — "한계값 정상 케이스", "상한 케이스", "N장 일반화 검증", "기존 동작 명세화".

**강조를 남발하지 않는다.** "절대 금지"를 여러 곳에 추가하면 실제 금지 사항이 드러나지 않는다.

## 문서 작성

문서·README·설계 문서·PR 본문·슬라이드·HTML 처럼 사람이 읽을 산문을 작성하거나 수정할 때는 `doc-writing` 스킬을 먼저 호출해 전체 규칙을 따른다.
문서 파일을 작성하거나 수정하기 전에 `doc-writing` 을 호출했는지는 훅(`doc-skill-guard.py`)이 확인한다. 같은 훅이 캐묻기도 확인한다. 이번 요청에서 캐묻기 스킬(`grill-me`·`grill-with-docs`)을 호출했거나 생략 지시를 받았는지, 아니면 같은 세션에서 캐묻기를 마친 뒤 작성한 문서인지를 확인한다.
새로 작성하거나 크게 수정한 문서를 커밋하기 전에 그 문서의 독자 테스트를 실행했는지는 훅(`stop-check.py`)이 확인한다.

대화 답변에는 아래 핵심을 늘 적용한다. 긴 설명을 작성할 때는 스킬을 호출한다.

- 전각 대시(—)로 두 문장을 연결하지 않는다.
- 문단 첫 문장을 굵게 표시하지 않는다. 굵기는 그 안에서 실제로 중요한 한 곳에만.
- 「A가 아니라 B」·「~기 때문입니다」 같은 틀을 연달아 사용하지 않는다.
- 비유·의인화를 사용하지 않는다. 도메인 명사에 상태 동사를 붙여 축약하지 않는다.
- 코드 상수나 영어 개념어를 직역한 한자어(활성·가용·순번·실측·슬라이스 등)를 사용하지 않는다. 호출·작성·수정·차단 같은 표준 업무 동사는 여기에 해당하지 않는다.
- 한 항목에 한 요점. 표 셀에 문장이 둘 이상이면 문장마다 줄을 바꾼다.
- ASD-STE100 의 작성 규칙을 따른다. 한 문장에 사실 하나. 문장은 어절 20개 안. 능동태. 같은 대상은 같은 낱말. 절차는 명령형, 설명은 평서문. 낱말 사전은 영어용이라 사용하지 않는다.
- 꾸민 문장을 작성하지 않는다. 완곡한 말(「~쪽입니다」「~로 잡습니다」), 인상 표현(「놀랄 만큼」), 군말을 삭제한다. 사실·판단·지시만 남긴다.

## ponytail

`ponytail` 플러그인이 `SessionStart`·`SubagentStart` 훅으로 **모든 세션·모든 저장소에 자동
주입된다.** 스킬을 호출하지 않아도 켜져 있고 기본 강도는 `full` 이다. 끄려면 메시지 전체를
`stop ponytail` 로 전송한다.

강도는 `full` 로 둔다. `ultra` 는 요구사항 자체를 먼저 검토하는데, 그건 「범위」의 「요청받은 것을
요청받은 범위로 낸다」와 충돌한다.

사다리 자체는 「범위」와 같은 말이라 충돌이 없다 — 요청에 없는 추상화·방어 코드를 추가하지 않고,
표준 라이브러리와 이미 설치된 의존성을 먼저 확인한다.

**이 문서가 우선한다.** ponytail 이 요구해도 아래는 따르지 않는다.

| ponytail 이 요구하는 것 | 이 문서 |
|---|---|
| 코드 먼저, 설명은 최대 세 줄 | 커밋 체크포인트의 작업 내역과 추천 커밋 명령, 슬라이스 완료 시 인수 확인 항목별 리스트업, 디버거로 본 값, 슬라이스 진행 표는 전문으로 제시한다. ponytail 자신의 「요청받은 설명은 부채가 아니다」에 해당한다 |
| 테스트 프레임워크·fixture 금지, `assert` 자체검사 하나 | 「TDD」 섹션이 우선한다. 사이클마다 커밋하고 그 저장소가 사용하는 테스트 도구를 사용한다. ponytail 의 테스트 섹션은 Python 전제다 |
| 구현이 하나뿐인 계층·추상화는 `yagni` | **그 저장소의 CLAUDE.md 가 확정한 계층·폴더·이름 규칙은 `yagni` 대상이 아니다.** 지금 호출자가 하나여도 마찬가지다. 규칙을 삭제한 diff 가 짧아 보이는 것은 근거가 되지 않는다 |
| 미룬 것은 `ponytail:` 주석으로 | 그 저장소가 이미 사용하는 마커를 사용한다. 마커를 두 종류로 늘리지 않는다 |

마지막 줄 때문에 **`/ponytail-debt` 는 대개 결과가 없다.** 그 스킬은 `(#|//) ?ponytail:` 만
grep 하므로 저장소 고유 마커를 찾지 못한다.

### review 는 쓰고 audit 은 안 쓴다

`/ponytail-review` 는 **diff 한정**이라 사용한다. 호출할 때 아래를 함께 읽는다.

**지적하지 않는다** — 그 저장소의 CLAUDE.md 가 확정한 것이라 「구현이 하나뿐」이 근거가 되지 않는다.

- 계층·폴더·이름 규칙에 따라 생성한 파일과 클래스 — 지금 호출자가 하나뿐인 것을 포함해서
- 규칙 하나에 테스트 하나씩 두는 구조
- 그 문서가 예외로 허용한 주석

**지적한다** — 태그는 ponytail 것을 그대로 사용한다.

- `stdlib:` 표준 라이브러리나 프레임워크가 이미 제공하는 기능을 직접 구현한 것
- `native:` 이미 설치된 의존성이 제공하는 기능을 새로 구현한 것
- `delete:` 호출되지 않는 코드, 아무도 설정하지 않는 설정 값, 이미 종료된 TODO
- `shrink:` 같은 로직을 더 짧게
- `yagni:` **위 「지적하지 않는다」에 없는** 추상화만

**그 저장소의 경계 규칙은 `boundary:` 를 추가해 검토한다.** CLAUDE.md 에 계층 경계가 명시되어 있으면
