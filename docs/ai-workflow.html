AI Workflow

최대현 · 백엔드 개발자 · github.com/Ting97ok

이 문서는 ai-global-rules 저장소의 규칙이 작업 흐름의 어느 단계에서 적용되는지 보여 준다. 요청부터 병합까지를 그림 여섯 장으로 나눴다. 이 흐름을 왜 이렇게 만들었는지는 회고 「AI와 일하며 가장 많이 고친 건 문서였다」에 기록했다.

요약

  • 역할: Claude가 설계 문서 초안과 구현을 작성한다. 개발자는 설계를 이해하고 리뷰하고 커밋한다. Codex(OpenAI의 코딩 에이전트)는 문서를 따로 읽고 검토한다.
  • 관문: 개발자가 설계 문서를 이해해야 구현을 시작한다. 사이클이 끝날 때마다 개발자가 리뷰해야 커밋한다.
  • 강제: 반드시 지킬 항목 가운데 기계로 확인할 수 있는 것은 훅이 Claude의 도구 호출과 답변에서 검사한다. 설계를 이해했는지와 검증 결과가 맞는지는 개발자가 판단한다.
  • 읽는 법
  • 1장 요청과 설계 초안
  • 2장 초안 검토와 확인
  • 3장 이해·토론과 드래프트 PR
  • 4장 TDD 사이클과 리뷰
  • 5장 인수 확인
  • 6장 전체 검토·반영·병합
  • 모든 장에 적용되는 장치

읽는 법

그림은 흐름을 세 단위로 나눈다.

  • 설계 문서: 기능 하나를 설명하고 구현을 여러 작업으로 나눈다.
  • 브랜치: 설계 문서가 나눈 작업 하나를 담는다. 다음 작업은 새 브랜치에서 시작한다.
  • 사이클: 브랜치 안에서 RED → GREEN을 한 번 진행하는 단위다.

  • 턴: 개발자 메시지 하나에 Claude가 한 번 답하는 단위
  • 세션: Claude Code(Anthropic의 코딩 에이전트) 대화 하나

  • 훅: claude/hooks/. 그림 아래 장치 설명에는 훅마다 적용 시점과 차단 대상·알림 내용만 기록했다. 검사 범위와 한계는 README 「자동 검사 범위」에, 세부 조건은 각 훅 파일 첫머리에 있다.
  • 전역 규칙: claude/CLAUDE.md.
  • 저장소 스킬: claude/skills/의 codex-cross-check·doc-writing. render-check.js는 doc-writing 폴더 안에 있다.
  • 외부 스킬: grill-me와 grill-with-docs는 mattpocock/skills에서 가져와 커스텀하여 사용한다. ij-debugger는 IntelliJ IDEA가 설치한 그대로 사용한다. 세 스킬은 저장소에 포함하지 않았다. 수정한 내용과 출처는 README의 「공개 범위」에 기록했다.
  • 플러그인 스킬: ponytail-review는 ponytail 플러그인, humanize 진단은 humanize-korean 플러그인의 스킬이다. 플러그인을 켜는 설정과 플러그인 저장소 주소는 claude/settings.json에 있다.

1장 요청과 설계 초안

개발자의 요청에서 시작한다. Claude는 개발자의 요청 범위·의도나 진행 상황이 모호하면 코드나 문서를 찾아보기 전에 먼저 질문한다. Claude는 문서를 작성하기 전에 누가 읽을 문서인지와 어떤 내용을 담을지 개발자에게 구체적으로 질문한다. 이 절차를 심층 인터뷰라고 부른다. 개발자의 답으로 Claude가 설계 문서 초안을 작성한다.

  1. ① 전역 규칙 「모호하면 먼저 질문」
    적용 시점
    개발자가 아는 사실(진행 상황·완료 여부·범위·의도)이 모호할 때
    역할
    Claude가 코드나 문서를 찾아보기 전에 개발자에게 먼저 질문한다.
  2. ② grill-me · grill-with-docs
    적용 시점
    Claude가 문서를 작성하거나 수정하기 전
    역할
    Claude가 누가 읽을 문서인지와 문체를 먼저 질문하고 담을 내용을 구체적으로 질문한다. 저장소 규칙 파일(CLAUDE.md)이 결정과 용어를 기록한 문서를 따로 지정했으면 grill-with-docs 로 그 문서와 대조해 질문한다.
  3. ③ doc-writing
    적용 시점
    Claude가 문서를 작성하거나 수정할 때
    역할
    문체·어휘·형식과 확인 절차의 규칙을 Claude에게 전달한다.
  4. ④ doc-skill-guard.py
    적용 시점
    Claude가 파일 편집 도구나 셸 명령(예: >·sed -i)으로 문서 파일을 작성하거나 수정하기 전
    차단 대상
    Claude는 문서를 작성하기 전에 doc-writing과 심층 인터뷰 스킬을 모두 호출해야 한다. 둘 중 하나라도 호출하지 않았으면 해당 편집이나 셸 명령을 차단한다.
    검사 생략 조건
    • 개발자가 요청이나 질문 창 답에 「심층 인터뷰 생략」을 별도의 한 줄로 기록하면 그 요청에서는 심층 인터뷰 확인을 생략한다. doc-writing 호출 여부는 그대로 확인한다.
    • 같은 세션에서 심층 인터뷰를 마친 뒤 그 문서를 수정하면 심층 인터뷰 확인을 생략한다.
  5. ⑤ prose-check.py: Claude가 .md·.html 문서를 작성하거나 수정한 직후 그 문서에서 아직 커밋하지 않은 줄만 검사한다. 파일 변경을 되돌리지 않고 위반을 Claude에게 알린다.
    검사예처리
    전각 대시로 두 문장 잇기초안을 먼저 쓴다 — 그다음 고친다Claude에게 오류로 알려 다시 수정하게 한다
    표 칸 한 줄에 문장 두 개막는다. 알린다.Claude에게 오류로 알려 다시 수정하게 한다
    연결어미 뒤 쉼표~지만, ~는데, ~하고,Claude에게 오류로 알려 다시 수정하게 한다

    제목 안의 개수근거 문서 두 편Claude에게 참고로 알린다
    잦은 「~기 때문」열 문장에 두 번 이상Claude에게 참고로 알린다

2장 초안 검토와 확인

독자 테스트는 작성 중인 문서에 대한 사전 지식이 없는 Codex에게 문서만 주고 작성자의 의도에 맞게 이해했는지 질문하는 절차다. 새로 작성하거나 크게 수정한 문서는 Claude가 개발자에게 질문하지 않고 첫 독자 테스트를 실행한다. Claude는 Codex의 답변과 함께 빠진 설명과 필요 없는 글을 받는다. Claude와 Codex가 피드백의 반영 여부를 각각 판단하고 결과를 대조한다. 두 판단이 불일치하면 Claude가 새 근거(파일 확인, 실행 결과, 원문 인용)를 찾아 다시 질문한다. 새 근거가 없으면 개발자가 결정한다.

수정한 뒤에는 정보를 바꾼 수정만 독자 테스트로 다시 확인한다. 정보를 바꾼 수정은 설명 추가, 결론·수치·절차 변경, 섹션 순서 변경이다. 이때 Codex에게는 바뀐 정보와 관련된 질문만 전달한다. 문체·낱말 통일, 문장 삭제, 오타 수정은 다시 확인하지 않는다.

공개 문서나 중요한 설계의 최종안이면 내용이 맞는지도 교차 검증으로 확인한다. Claude가 먼저 답을 기록해 두고 Codex는 그 답을 모르는 채 같은 질문에 답한다. 두 답이 불일치하면 2~3회 다시 질문한다. 그래도 합의하지 못하면 개발자가 결정한다.

그 뒤 Claude가 어휘, AI 문체, 실제 화면을 차례로 확인한다. 어휘 대조는 Claude가 심층 인터뷰에서 결정한 문체에 동사가 맞는지 확인하는 절차다. 명사·동사·한자어가 보통 사람이 같은 뜻으로 사용하는 말인지도 하나씩 확인한다. 개발자는 그 뒤 3장에서 최종 문서를 리뷰한다.

  1. ① codex-cross-check
    적용 시점
    개발자가 교차 검증을 요구할 때, 개발자의 리뷰에 답할 때, 공개 문서나 중요한 설계 판단의 최종안을 제시할 때, 독자 테스트 피드백의 반영 여부를 결정할 때
    역할
    • Claude가 세션의 첫 호출 전에 Codex 모델과 추론 수준을 개발자에게 질문한다.
    • Claude가 Codex의 남은 사용량을 확인하고 이전 맥락을 모르는 새 작업으로 요청한다.
    • Claude가 Codex 호출을 crosscheck.py run 으로 감싸 실행한다. crosscheck.py 가 호출마다 Codex 세션 ID·모델·추론 수준·사용량을 기록한다.
    • Claude가 항목마다 주고받은 내용의 요지를 crosscheck.py note 로 기록한다. report 출력으로 답변에서만 보고하고 PR 댓글로 게시하지 않는다.
  2. ② render-check.js
    적용 시점
    슬라이드처럼 크기가 정해진 문서를 렌더링해 확인할 때
    역할
    장마다 넘침·잘림·바닥 여백·겹침을 측정한다.

3장 이해·토론과 드래프트 PR

개발자가 설계 문서를 읽고 이해한 것만 구현으로 넘긴다. 이 관문을 둔 이유는 회고 1장에 기록했다.

이해하지 못하면 개발자가 질문하고 Claude가 설명하거나 설계 문서를 수정한다. 개발자는 이해했는지 다시 확인하고 이해할 때까지 이 토론을 반복한다. 4·5장에서 설계 허점을 찾으면 이 토론으로 온다. 토론이 끝나면 원래 장으로 돌아간다.

토론 중에 Claude가 설계 문서의 정보를 바꾸면 2장 독자 테스트부터 다시 진행한다. Claude는 설계 문서 커밋 명령을 제시하기 전에 마지막 독자 테스트 뒤의 수정이 있는지 확인한다. 수정이 있으면 독자 테스트 실행 여부를 질문 창(Claude Code가 선택지를 보여 주고 답을 받는 창)으로 개발자에게 질문한다. 개발자는 「실행」과 「독자 테스트 생략」 가운데 하나를 선택한다.

이해하면 Claude가 빈 커밋으로 브랜치를 시작하고 드래프트 PR(작업 중이라 아직 병합하지 않는 PR)을 여는 명령을 제시한다. 개발자가 그 명령을 실행한다. 설계 문서를 처음 커밋하는 브랜치에서는 설계 문서가 빈 커밋 다음의 첫 커밋이 된다. 6장에서 돌아온 다음 브랜치는 빈 커밋 뒤에 바로 4장 RED로 간다.

구현이 여러 작업으로 나뉘면 설계 문서만 담은 이 브랜치를 먼저 병합하고 구현 브랜치를 새로 연다.

  1. ① stop-check.py
    적용 시점
    Claude가 답변을 끝내기 전
    차단 대상
    Claude가 실행한 명령이나 답변 내용이 아래에 해당하면 답변을 반려한다. git -C 경로 처럼 전역 옵션을 준 git 명령도 같은 명령으로 판정한다.
    • 이번 턴에 상태 확인 명령(git status·log·diff·branch·rev-parse, gh pr view·list·status)을 하나도 실행하지 않고 스테이징·커밋·푸시·PR 명령을 제시했다.
    • 이번 턴의 마지막 테스트가 실패했는데 스테이징·커밋·푸시·PR 명령을 제시했다. 빈 커밋 명령은 제외한다.
    • 현재 대화에서 수정한 문서를 새 파일이나 추가·삭제 합 50줄 이상으로 커밋하는데 마지막 수정 뒤에 그 문서의 독자 테스트를 끝까지 실행하지 않았다. 이 조건으로 반려되면 Claude가 독자 테스트 실행 여부를 개발자에게 질문 창으로 질문한다.
    • 커밋 메시지에 「검토:」 줄이 있는데 같은 명령 블록에 PR 댓글 주소가 없다.
    • PR 댓글을 게시하고 커밋 명령을 제시했는데 git push 블록이 없다.
    • 개발자에게 cat·grep 같은 조회 명령으로 시작하는 블록을 제시했다.
    • 교차 검증의 Codex 작업을 crosscheck.py run 으로 감싸지 않고 호출했다. 독자 테스트는 제외한다.
    • crosscheck.py note 로 기록한 교차 검증 항목의 제목이 그 뒤 답변 어디에도 없다.
    검사 생략 조건
    개발자가 질문 창에서 「독자 테스트 생략」을 선택하거나 마지막 메시지에 이 말을 별도의 한 줄로 기록하면 독자 테스트 확인을 생략한다.

4장 TDD 사이클과 리뷰

Claude가 RED와 GREEN을 이어서 진행하고 체크포인트 보고를 제시한다. 보고의 커밋 명령은 테스트만 담은 RED 커밋과 구현을 추가한 GREEN 커밋으로 나뉜다. 개발자는 사이클이 끝날 때마다 한 번 리뷰한다. 브랜치의 마지막 사이클을 커밋하면 Claude가 설계 문서와 README 같은 저장소 문서를 한 번에 갱신하고 5장 인수 확인으로 간다.

피드백이 오면 Claude는 방향이 바뀌었는지 먼저 판단한다. 개발자의 반박으로 Claude의 결정이 바뀌면 방향이 바뀐 것이다. 피드백에 따라 아래 순서로 진행한다.

피드백순서
방향 유지Claude 수정 → 체크포인트 보고 → 개발자 리뷰·커밋
방향 변경개발자가 쌓인 커밋 푸시 → Claude가 PR 댓글 작성 → Claude 수정 → 체크포인트 보고 → 개발자 리뷰·커밋·푸시

댓글이 없는 커밋은 모아 두었다가 다음 PR 댓글을 게시하기 전이나 병합하기 전에 푸시한다.

개발자가 여러 항목의 리뷰를 전달하면서 수정하라고 하지 않았으면 Claude는 항목마다 수용 여부와 변경 내용을 먼저 답한다. 개발자가 확인한 뒤에 수정한다.

  1. ① commit-checkpoint.py
    적용 시점
    Claude가 셸 명령을 실행한 직후
    알림 내용
    Claude가 실행한 테스트·빌드가 통과했는데 이번 세션에서 수정한 파일이 커밋되지 않고 남으면 다음 사이클 RED 대신 체크포인트 보고를 제시하라고 Claude에게 지시한다.
  2. ② git-guard.py
    적용 시점
    Claude가 셸 명령을 실행하기 전
    차단 대상
    git add -A, git add --all, git add . 을 차단한다. git -C 경로 add -A 처럼 전역 옵션을 준 git 명령도 차단한다.
  3. ③ stop-check.py: 체크포인트 보고의 스테이징·커밋 명령을 검사한다. 이번 턴의 마지막 테스트가 실패했거나 상태 확인 명령을 실행하지 않았으면 답변을 반려한다. 전체 조건은 3장 ①에 있다.
  4. ④ stop-check.py
    적용 시점
    Claude가 커밋 명령을 제시한 뒤 받은 요청에 답변을 끝내기 전
    차단 대상
    PR 댓글 작성 여부를 판단하지 않은 답변을 반려한다. 판단 여부는 답변에 「댓글」이라는 말이 있는지나 댓글을 게시했는지로 확인한다.
  5. ⑤ git-guard.py
    적용 시점
    Claude가 PR 댓글을 게시하기 전
    차단 대상
    아래에 해당하면 댓글 게시를 차단한다.
    • 푸시하지 않은 커밋이 있다.
    • 「변경 파일:」 줄에 없는 추적 파일에 커밋하지 않은 변경이 있다.
    • 「교차 검증 지적:」 줄이 있다.
    • 「사용자 피드백:」 줄이 둘 이상이다.
    • 결정 항목 줄 하나에 문장이 둘 이상이다.
  6. 개발자 커밋: 개발자가 실행하는 명령에는 훅이 적용되지 않는다. 명령은 체크포인트 보고에서 검사를 거쳤다.
  7. PR 댓글 규칙
    • Claude가 gh pr comment 로 게시한다.
    • 댓글을 게시하기 전에 개발자가 쌓인 커밋을 먼저 푸시한다. 쌓인 커밋을 댓글 뒤에 함께 푸시하면 모두 댓글 아래에 붙어 어느 커밋이 결정을 반영했는지 구분할 수 없다.
    • 댓글 뒤의 수정 커밋은 푸시까지 진행한다. 그래야 PR 타임라인에서 댓글 아래에 그 커밋이 붙는다.
    • 댓글이 없는 커밋은 모아 두었다가 다음 PR 댓글을 게시하기 전이나 병합하기 전에 푸시한다.
    • 첫 줄에는 어느 작업에서 나온 피드백인지 기록한다. 그 아래는 다섯 줄이다: 1차 AI 결정 / 사용자 피드백 / 2차 AI 결정(피드백 반영) / 2차 AI 결정 근거 / 변경 파일.
    • 줄마다 한 문장으로 작성하고 변경 파일은 이름만 기록한다.
    • 피드백이 여러 건이면 건마다 따로 게시한다.
    • 댓글로 게시한 결정이 다시 바뀌면 후속 댓글을 게시한다. 첫 줄에는 어느 결정이 바뀌었는지 기록하고 그 아래는 다섯 줄이다: 직전 결정 / 다시 바뀐 계기 / 새 결정 / 새 결정 근거 / 변경 파일.
    • 방향을 바꾼 커밋은 메시지 본문 첫 줄을 「검토:」로 시작해 무엇이 어떻게 바뀌었는지 기록하고 댓글 주소를 추가한다.
    • 개발자가 Claude가 제시한 선택지를 고른 것은 댓글로 게시하지 않는다. 다만 앞서 댓글로 게시한 결정이 다시 바뀌면 게시한다.
    • Codex 교차 검증 결과는 댓글로 게시하지 않는다.

5장 인수 확인

문서 갱신까지 마치면 Claude가 앱을 기동해 운영과 같은 경로로 호출한다. 정상·경계·거부·오류 응답을 모두 확인하고 결과를 체크포인트 보고에 항목별로 기록한다. 개발자가 리뷰해 통과하면 커밋하고 6장으로 간다.

피드백이면 4장에서 수정한다. 수정한 뒤 커밋하기 전에 이 장으로 돌아와 인수 확인을 다시 진행한다. 설계 허점이면 3장 토론으로 간다.

  1. ① ij-debugger
    적용 시점
    JVM 프로젝트의 앱을 IntelliJ IDEA 디버거로 기동해 확인할 때
    역할
    IDEA 디버그 실행·로그포인트·중단점으로 실제로 흐른 값과 분기를 확인한다. 로그포인트는 실행을 멈추지 않고 값만 기록하는 중단점이다. 디버거 도구가 없으면 Claude가 그 사실을 먼저 알린다.
  2. ② git-guard.py
    적용 시점
    Claude가 셸 명령을 실행하기 전
    차단 대상
    git add -A, git add --all, git add . 을 차단한다. git -C 경로 add -A 처럼 전역 옵션을 준 git 명령도 차단한다.
  3. ③ stop-check.py: 인수 확인 보고의 [Docs]·수정 커밋 명령을 검사한다. 새 문서나 크게 수정한 문서를 커밋하는데 마지막 수정 뒤에 독자 테스트를 실행하지 않았으면 답변을 반려한다. 반려되면 Claude가 독자 테스트 실행 여부를 개발자에게 질문한다. 전체 조건은 3장 ①에 있다.

6장 전체 검토·반영·병합

인수 확인을 통과한 브랜치를 Claude 리뷰와 개발자 자체 리뷰로 따로 검토한다. 개발자가 두 결과를 대조해 반영할 피드백을 결정한다. 반영할 피드백이 있으면 Claude가 반영하고 5장 절차로 인수 확인을 다시 진행한 뒤 리뷰를 받는다. 반영할 피드백이 없거나 리뷰를 통과하면 Claude가 PR 본문을 작성한다. 개발자가 스쿼시로 병합한다.

남은 작업이 있으면 3장으로 돌아가 새 브랜치를 연다. 남은 작업이 없으면 설계 문서가 다룬 기능 전체를 Claude와 개발자가 각각 검토한다. 개발자가 두 결과를 대조해 반영할 피드백을 결정한다. 반영할 피드백이 있으면 3장에서 새 브랜치를 열어 수정한다.

  1. ① ponytail-review
    적용 시점
    Claude가 브랜치의 변경 전체를 리뷰할 때
    역할
    diff 만 검토한다. 표준 라이브러리나 이미 설치된 의존성으로 대신할 수 있는 코드, 사용하지 않는 코드, 과한 추상화를 찾는다.
  2. ② stop-check.py: 대조 결과를 받은 뒤의 답변을 검사한다. PR 댓글 작성 여부를 판단하지 않았으면 답변을 반려한다. 전체 조건은 4장 ④에 있다.
  3. ③ git-guard.py
    적용 시점
    Claude가 셸 명령을 실행하기 전
    차단 대상
    git add -A, git add --all, git add . 을 차단한다. git -C 경로 add -A 처럼 전역 옵션을 준 git 명령도 차단한다.
  4. ④ stop-check.py: 반영 보고의 커밋 명령을 검사한다. PR 댓글을 게시했는데 git push 블록이 없거나 「검토:」 줄에 댓글 주소가 없으면 답변을 반려한다. 전체 조건은 3장 ①에 있다.
  5. ⑤ stop-check.py: PR 본문·병합 명령을 제시하는 답변을 검사한다. 이번 턴에 상태 확인 명령(git status·log·diff·branch·rev-parse, gh pr view·list·status)을 하나도 실행하지 않았으면 답변을 반려한다. 전체 조건은 3장 ①에 있다.

모든 장에 적용되는 장치

아래 셋은 특정 단계가 아니라 작업 내내 적용된다.

  • settings.json: Claude가 실행하는 명령 가운데 rebase, force push, reset, checkout --, restore, clean, stash drop, stash clear, branch -D, rm -r 을 차단한다. git -C 경로 reset 처럼 전역 옵션을 준 git 명령도 차단한다. PR 브랜치 이력을 다시 쓰면 댓글과 커밋의 연결이 끊긴다. Codex 규칙은 전역 옵션 뒤의 하위 명령을 구분하지 못해 git -C·git -c·git --no-pager 로 시작하는 명령은 실행 전에 개발자에게 승인을 요청한다.
  • agent-guard.py: Claude가 일을 나눠 맡기는 서브에이전트를 호출할 때 모델을 지정하면 차단한다. 서브에이전트는 세션의 모델을 그대로 사용한다.
  • memory-note.py: Claude가 대화 사이에 기록하는 파일(메모리)에 기록한 뒤 그 내용을 전역 규칙이나 저장소 문서에 둘지 다시 확인하게 알린다. 차단하지 않는다.

이 흐름을 만든 과정과 아직 답을 내리지 못한 것은 회고에 기록했다. 규칙·훅·스킬 파일 목록과 자동 검사 범위는 저장소 README에 있다.
