AI와 일하며 가장 많이 고친 건 문서였다

최대현 · 백엔드 개발자 · github.com/Ting97ok

이 글은 ai-global-rules 저장소의 규칙이 만들어진 과정을 기록한 회고다. 나는 실무와 개인 프로젝트에서 Claude Code와 Codex에 설계 문서 초안과 구현을 맡기고 판단과 검토는 직접 진행해 왔다. 그렇게 일하며 부딪힌 문제와 그때 결정한 내용을 기록한다.

요약

  • 원칙: AI가 세운 구현 계획을 온전히 이해한 뒤에 구현을 시작하기로 했다.
  • 병목: 이 원칙을 지키다 보니 가장 큰 병목은 AI가 작성한 읽기 어려운 구현 계획 문서였다.
  • 대응: 문서 규칙과 형식을 계속 수정했고 Claude Code에서는 반드시 지킬 항목을 훅(정해진 조건에서 반드시 실행되는 검사 스크립트)으로 확인하게 했다.
  • 결과: AI가 작성한 글을 읽는 부담이 줄었다. 설계와 컨벤션 리뷰, 놓칠 수 있는 예외 검토에 시간을 더 쓰면서 틀린 설계를 구현 도중에 바로잡을 수 있었다. 효과를 수치로 나타내지는 않았다.

내 작업 흐름은 아래와 같다. 이 글은 그 가운데 첫 관문, 설계 문서를 이해하는 일에서 생긴 문제를 다룬다.

1. 구현보다 이해가 먼저

AI가 구현 계획을 제시하면 바로 코드부터 작성하게 하지 않는다. 내가 그 계획을 온전히 이해한 다음에야 구현으로 넘어간다. 초안은 AI가 작성하더라도 무엇을 받아들이고 구현할지는 결국 내가 판단하고 책임져야 하기 때문이다. 이 원칙을 지키다 보니 가장 큰 병목은 AI가 작성한 구현 계획 문서를 읽는 일이었다.

2. 일관성 챙기기: 코드는 모범 사례로, 문서는 규칙으로

코드는 모범 코드와 함께 모범 코드와 다르게 가야 하는 경우를 예외 규칙으로 주면 대체로 저장소 구조를 따른다. 설계와 컨벤션에 맞는지 리뷰하고 내 판단과 다를 때만 근거를 맞대 보고 코드를 수정한다. 문서는 달랐다. 코드는 컴파일러와 테스트가 틀린 곳을 알려 주지만 문서가 읽기 어렵다는 건 읽는 내가 아니면 알 수 없었다.

구분코드문서
모범을 주면큰 틀을 따른다.겉의 틀만 비슷해진다.
리뷰에서 수정하는 것설계·컨벤션이 내 판단과 다른 곳AI 특유의 문체, 필요 없는 요약, 장황한 설명, 단어 선택

규칙으로 하나씩 짚지 않으면 같은 문장을 여러 번 읽어야 뜻을 이해할 수 있었다. 그래서 코드는 모범 사례로, 문서는 규칙으로 일관성을 구현했다.

3. 문서 형식 변천사

가독성을 1순위로 문서 형식을 단계적으로 변경했다. 처음에는 읽는 자리를, 그다음에는 화면 배치를, 마지막으로 분량을 바꿨다.

형식바뀐 것얻은 것남은 문제
1계획 문서AI 도구가 대화창에 제시하는 기본 계획 형식으로 시작했다.-가독성이 너무 떨어져 읽기를 포기하는 일이 생겼다.
2Markdown읽는 자리: 대화창 속 텍스트에서 따로 여는 문서로 옮겼다.표와 제목 구조가 생기고 큰 화면에서 볼 수 있었다.긴 글의 흐름은 그대로였다.

슬라이드로 바꾸고 나서 AI가 작성한 글을 읽는 스트레스가 줄었다. 생산성도, 일을 이어 갈 체력도 나아졌다고 느낀다.

작업하면서 보는 개인용 문서는 슬라이드로, 공개용 문서는 블로그 글처럼 스크롤해서 읽는 형태로 작성한다. 나는 슬라이드가 편하지만 처음 보는 사람이 맥락을 따라가기에는 블로그 글 형태가 더 익숙할 거라고 생각했다. 형식을 가른 기준은 독자였다. 2026년 9월부터는 문서를 작성하기 전에 독자를 먼저 결정한다.

4. 문서 규칙은 스킬로, 강제할 항목은 훅으로

문서 규칙은 문서를 작성할 때만 호출되도록 스킬로 옮기고 반드시 지켜야 할 항목은 Claude Code 훅으로 확인하게 했다.

스킬

스킬은 필요할 때만 호출해 읽는 지시 파일이다. Claude는 평소에 스킬의 이름과 설명만 알고 있다가 작업이 설명과 맞으면 스킬을 호출해 본문을 읽는다.

Claude Code 문서는 매 세션 불러오는 규칙 파일이 길면 컨텍스트(AI가 한 번에 읽는 대화와 파일의 양)를 더 사용하고 지시를 덜 지킨다고 설명한다. 그래서 문서 작성 규칙은 전역 규칙 파일에서 떼어 내 doc-writing 스킬로 옮기고 대화에도 필요한 핵심 원칙만 전역 규칙에 남겼다.

스킬 이름을 호출하지 않아도 문서 작업이면 자동으로 호출되도록 스킬 설명을 작성했다. 문서 파일을 작성하기 전에 스킬을 호출했는지는 훅이 한 번 더 확인한다. Codex가 읽는 위치에 전역 규칙과 스킬 원본을 가리키는 파일 링크(심볼릭 링크)를 두어 두 도구가 같은 원본을 읽게 한다. 훅은 동작을 확인한 것, 확인하지 못한 것, 입력·기록 형식 차이로 검사하지 못하는 것이 있어 적용 범위를 README에 따로 기록했다. 규칙 전문은 저장소 README에서 볼 수 있다.

훅

Claude Code 문서는 규칙 파일의 지시는 권고이고 훅은 정해진 조건에서 반드시 실행된다고 설명한다. 그래서 금지하거나 되돌려야 할 동작은 훅과 설정으로 검사한다.

2026년 9월에 문서 규칙 둘을 추가하고 Claude Code 훅으로 강제했다. 작성하기 전에는 독자와 문체, 담을 내용을 개발자에게 질문한다. 이 절차를 심층 인터뷰라고 부른다. 작성한 뒤에는 독자 테스트를 실행한다. 독자 테스트는 문서 사본만 읽는 Codex에 질문에 답하게 해서 빠진 설명과 필요 없는 글을 찾는 절차다.

새로 작성하거나 크게 수정한 문서는 Claude가 나에게 질문하지 않고 첫 독자 테스트를 실행한다. 그 뒤에는 설명 추가나 결론·수치·절차 변경처럼 정보를 바꾼 수정만 다시 확인한다. Claude와 Codex가 지적의 반영 여부를 각각 판단하고 결과를 대조한다. 두 판단이 불일치하면 Claude가 새 근거(파일 확인, 실행 결과, 원문 인용)를 찾아 다시 대조하고 새 근거가 없으면 내가 결정한다. 커밋하기 전에 마지막 독자 테스트 뒤의 수정이 있으면 Claude가 독자 테스트 실행 여부를 나에게 질문한다. 나는 최종 문서를 리뷰한다.

규칙 문장만으로는 AI가 둘을 지키지 않았다. 문서를 이해할 수 없으면 1장의 원칙을 지킬 수 없다. 그래서 두 규칙을 확인하는 훅을 만들었다. Codex로 문서를 작성할 때는 이 두 규칙을 훅이 확인하지 않는다.

5. AI는 설계와 검토의 파트너

AI에게 구현을 맡기지만 가장 많이 이야기하는 때는 설계하고 검토할 때다. 기능·아키텍처·ERD 설계를 함께 토론하고 구현 중에는 컨벤션과 놓칠 수 있는 예외를 같이 다시 본다. 목표는 혼자 만드는 제품의 완성도를 끌어올리는 것이다. 여기서 완성도는 출시 시점의 품질과 유지보수성을 모두 뜻한다.

작업 흐름

이 흐름을 여섯 장으로 나눈 그림은 AI Workflow 문서에 있다. 아래는 단계마다 내가 직접 하는 일이다.

  1. 설계

    기능 설계, 아키텍처 설계, ERD 설계처럼 깊은 판단이 필요한 부분에 가장 많은 시간을 쓴다. AI와 토론하며 결정하고 이해한 계획만 구현으로 넘긴다. 계획 문서는 독자를 먼저 결정한 뒤에 작성하고 구현으로 넘기기 전에 독자 테스트로 빠진 설명을 찾는다.

    face-gate는 아파트 단지 출입용 얼굴 인식 단말 연동 서버다. 오픈 후 코드를 바꾸면 100여 단지에 다시 배포해야 해서, 구현 전에 범위·기술 스택·프로토콜·기능·오류 응답·ERD·일정 문서를 먼저 작성했다. 폐기한 대안에도 다시 검토할 조건을 기록했다.

  2. 구현

    작업 단위마다 브랜치를 나눈다. 테스트 하나와 구현 하나를 번갈아 작성하는 사이클이 끝날 때마다 코드를 한 번 리뷰하고 테스트와 구현을 따로 커밋한다. 놓칠 수 있는 예외가 떠오르면 그 자리에서 AI와 토론한다. 리뷰에서 설계 허점을 찾으면 구현을 멈추고 재설계할지 기술 부채로 남길지 결정한다.

    공개 기록: hotdeal-commerce의 테스트 커밋 82a62aa와 구현 커밋 78982d6

  3. 인수 확인

    작업 단위가 끝나면 AI가 앱을 IntelliJ 디버거로 기동해 실제 경로로 호출한다. 나는 그 과정을 IntelliJ 화면에서 확인한다. 디버거를 사용하는 이유는 두 가지다. 첫째, AI가 디버거로 무엇을 하는지 내가 보고 있는 IntelliJ 화면에서 직접 볼 수 있다. 둘째, 코드를 작성하지 않고도 확인할 수 있는 경우가 생각보다 많다.

    face-gate 실단말 테스트에서는 중단점에서 멈춘 뒤, 서버에 아직 구현하지 않은 명령을 디버거에서 직접 전송했다.

    공개 기록: hotdeal-commerce PR #6 본문의 「인수 확인」

    3-1. 설계가 틀렸다고 판단되면

    인수 확인 중에 기존 설계가 틀렸다고 판단할 때가 있다. 일정에 조금이라도 여유가 있으면 리팩터링 작업 단위를 추가해 설계를 수정한다. 여유가 없으면 그 설계 허점을 기술 부채로 허용할 수 있는지 검토한다. 허용할 수 있으면 기술 부채로 남긴다. 허용할 수 없는 허점이면 일정이 촉박해도 수정한다.

    사람이 직접 하면 오래 걸렸을 리팩터링을 AI와 함께 진행해 체감상 생산성이 대폭 향상되었다.

    face-gate에서는 실단말 확인 중 성공 응답이 곧 사진을 인식할 수 있다는 뜻은 아님을 알게 됐다. 그래서 단말이 보고하는 사진 수와 템플릿 수의 차이를 등록 실패 수로 보기로 했다. 먼저 두 값을 지표로 노출한다. 차이가 벌어지면 템플릿 생성 검증을 다시 검토한다. 템플릿은 단말이 사진을 자기 인식 알고리즘에 맞게 변환한 파일이다. 사진에서 얼굴이 작으면 단말은 사진을 저장하고 성공 응답을 주지만 템플릿은 만들지 않는다.

  4. 전체 검토

    작업 단위의 브랜치를 병합하기 전에 AI에게 리뷰를 맡기고 나도 빠진 곳이 없는지 전체를 자체 리뷰한다. 설계 문서의 작업 단위를 모두 병합하면 같은 방식으로 기능 전체를 한 번 더 검토한다. 가장 깊게 보는 것은 놓친 예외다.

  5. 교차 확인

    AI 리뷰와 자체 리뷰를 대조하고 필요한 지적과 필요 없는 지적을 가려 정리한 뒤 작업을 마무리한다.

출시 시점이 중요할 때

출시 시점이 중요한 사업이라면 설계와 검토에 쓰던 시간을 줄여 기간을 앞당길 수도 있다. 예외 처리에 시간을 쓰다가 출시 시점을 놓치면 사용자 없는 서비스가 될 수도 있다. 무엇에 시간을 쓸지는 속도와 결함 비용을 함께 보고 결정한다.

6. 아직 답을 내리지 못한 것

  • 문서 형식을 바꾼 효과를 수치로 나타내지 않았다. 비교 조건이 없다. 같은 문서를 변경 전 형식과 변경 후 형식으로 읽어도 두 번째에는 이미 내용을 알고 읽는다. 문서는 매번 다르다. 승인까지 걸린 시간이나 다시 질문한 횟수는 문서 길이와 주제에 더 크게 좌우된다. 읽기 편해졌다는 건 작업하며 느낀 변화다.
  • 슬라이드로 바꾸고 나서 다시 질문하는 일이 늘었다. 읽는 부담을 줄이려던 선택이 이해에 필요한 정보까지 줄였는지는 아직 모르겠다. 문서만 읽는 검토자로 확인하기 시작했다. 검토자는 Codex다. 사람이 읽으면 다른 결과가 나올 수 있다.

    2026-09-17 · 설계 문서 한 편의 사본을 Codex에 주고 질문 10개에 문서 문장을 인용해 답하게 했다. 지적 11건 가운데 실제 결함은 5건이었다. 설명 없이 사용한 내부 용어, 풀지 않은 약어, 두 뜻으로 읽히는 문장, 앞뒤가 어긋난 서술이다. 나머지는 검토자가 잘못 읽었거나 독자에 따라 판단이 다른 것이라 반영하지 않았다. Codex가 질문 10개에 모두 답하는 데 5분쯤 걸렸고 Codex 요금제에서 5시간마다 초기화되는 사용량 한도의 3%를 사용했다. 소요 시간과 사용량은 AI가 측정한 값이고 문서에 따라 달라진다.

    2026-10-08 · 9월 17일부터 10월 2일까지 독자 테스트를 88회 실행했다. 완료 기록이 있는 80회에 모두 301분이 걸렸고 한 번에 걸린 시간의 중앙값은 3분 16초였다. 한 문서에 가장 많이 실행한 횟수는 24회였다. 횟수와 시간은 AI가 Claude 대화 기록에서 집계한 값이다.

  • 문서 규칙은 문제가 보일 때마다 늘고 있다. 규칙이 많아질수록 AI가 지시를 덜 지키게 되지 않을까 하는 걱정도 있다.

    2026-09-17 · 심층 인터뷰와 독자 테스트를 추가하면서 문서 규칙이 또 늘었다. 강제할 항목은 훅으로 옮겼지만 규칙 문장은 줄지 않았다.

    2026-09-21 · AI Workflow 문서를 리뷰하며 문서 규칙을 또 추가했다. 커밋 직전에는 독자 테스트를 한 번 더 실행한다. 규칙 파일의 말을 문서로 옮길 때는 빠진 주체와 조건을 채운다. 규칙 문장은 이번에도 줄지 않았다.

    2026-10-08 · 독자 테스트 실행 기록을 보고 커밋 직전마다 다시 실행하던 규칙을 없앴다. 이제 정보를 바꾼 수정만 다시 확인한다. 교차 검증 기록에서 Claude와 Codex가 판단을 대조한 항목 100개는 72개가 첫 대조, 26개가 두 번째 대조에서 끝났다. 기록이 세 번째 차례까지 이어진 2개는 하나를 내가 결정했고 다른 하나는 Codex에 다시 질문하지 않고 화면 캡처라는 새 근거로 결정했다. 그래서 판단이 불일치하면 새 근거를 찾아 다시 대조하고 새 근거가 없으면 내가 결정하게 했다. 실행 횟수를 줄이는 변경이지만 규칙 문장은 이번에도 줄지 않았다.
